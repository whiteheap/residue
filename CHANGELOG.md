# Changelog

## Unreleased

- Tests (#8): `scripts/contract-check.sh` runs `remove` with no prompt against real Git, one repository per case, and pins its contract: the exit status (0; 3 for a refusal, a skip or an invalid target; 2 for a usage error), one `residue.remove/v1` document on stdout with the per-target result, reason and failing check ids, diagnostics on stderr only, and afterwards the file bytes, the registration, the branch, an unrelated worktree and no leftovers. 17 cases; a setup failure stops it with status 2, never as a product result. CI runs it on macOS, Linux and FreeBSD (as root and as an ordinary user).
- Tests (#9): the first in-crate tests, for the verdict fold in `Report::finish`, on synthetic checks only. No checks is `unknown`; a failed check keeps; an unknown one without a failure is `unknown`; a failed check outranks an unknown one; stale outranks every check; only passing checks make a candidate. Every set of up to five checks is compared with that contract, order never changes the verdict, and adding a failed or unknown check never yields a candidate. CI runs `cargo test --locked` on macOS and both Linux runners.
- README: FreeBSD has a prebuilt x86_64 binary on every release since 0.0.5; the README still said it had none.
- Fix (#7): `watch` chose a worktree because its upstream branch was gone, but the removal child did not know why, so an upstream that came back between the scan and the removal did not keep the worktree. `remove --only-if-upstream-gone` now carries that reason: the child removes a worktree only when the local refs show its branch's upstream gone, checked at the plan, in the re-check right before the move, and after the move right before the deletion. An upstream that exists, no upstream, a detached HEAD or a failed lookup keeps the worktree, with the reason in JSON and the text output, and exit status 3. `watch` passes it for work-landed removals only. Manual `remove` and disk-pressure removals are unchanged. residue still never fetches, so a remote change that has not reached the local refs is not seen. `--only-if-upstream-gone` with `--all`, or outside `remove`, is a usage error.
- The third read comes after the move aside and the re-measure, which can take seconds on a large worktree. If the upstream is back by then, the worktree goes back in place. Every way the requirement keeps a worktree, including a failed lookup, is `skipped`.
- Work landed now needs a remote-tracking upstream. A local upstream (`branch.NAME.remote` set to `.`) whose branch was deleted made a worktree look landed; `--only-if-upstream-gone` keeps it, and `watch` no longer picks it. `scan --json` and `explain --json` gain `upstream_ref`, the upstream's full refname (`refs/remotes/origin/fix`), and `watch` reads it.
- Fix: an upstream counted as gone whenever Git marked it `[gone]`, which Git also does when the ref exists but does not resolve to a commit (it names a tree, or it is a symbolic ref to a missing ref). It now counts as gone only when its ref is absent; anything else is a lookup error. `scan`'s `upstream_gone` follows, so `watch` no longer picks such a worktree, and `--only-if-upstream-gone` keeps it.

## 0.0.5 (2026-11-07)

Deletes what you saw, or nothing, and makes a scheduled sweep reversible. Until 0.0.4, `remove` re-ran the checks right before acting, but it compared the verdict, HEAD, branch, lock and the set of ignored entries, not what they held. Measured with `scripts/race-check.sh` against the 0.0.4 release binary: a file added inside `node_modules/` while the prompt waited was deleted with the worktree (exit 0). And a scheduled sweep that took a paused agent's worktree took it for good.

- Decision, the plan is a record: for each worktree it now keeps HEAD, the branch, the lock, the staged, modified and untracked files, the file count, size and newest modification time of every ignored entry, and the modification times of the worktree's `index` and `logs/HEAD`. Right before acting, residue compares a fresh record with it and skips on any difference, with a reason that names the difference: `node_modules/ changed since you confirmed (1,204 -> 1,388 files)`, `HEAD changed since you confirmed (a82c15ee7687 -> 55c48105f23a)`, `changed since you confirmed: 1 untracked`. Under `--yes` the reason says `since the plan`. `logs/HEAD` is fine here although `--idle` must not use it: a `git gc` between plan and removal only makes residue skip.
- Decision, move aside before deleting: after the re-check, `git worktree move` renames the worktree to a hidden sibling, `.NAME.residue-removing-PID`, and residue locks it with the reason `residue: removing`. `git worktree move` is one rename by Git that updates only this worktree's record, and it refuses another filesystem instead of copying; residue skips a worktree that is a mount point. Not `mv` plus `git worktree repair`: `repair` rewrites the records of every worktree of the repository. At the new path residue checks again: Git lists it there with the planned HEAD, branch and residue's lock, a new process snapshot sees nobody inside it, and the record still matches. Then it unlocks it and `git worktree remove`, without `--force`, deletes it. On any difference or failure it moves the worktree back and unlocks it (`...; it is back in place`). This narrows the window between the last check and the deletion; it does not close it. From that check until Git finishes, a process that opens the hidden directory by its new name, or one the probe cannot see, can still write into it, and the write is deleted with it. The README says so.
- A run killed partway leaves the worktree under its hidden name, still registered. `scan` lists it under `interrupted removals` with the one command that puts it back (`git -C MAIN worktree unlock HIDDEN && git -C MAIN worktree move HIDDEN ORIGINAL`, or `git worktree remove HIDDEN` when the directory is gone), and says when the PID that moved it still runs. Neither a sweep nor `remove PATH` touches such a worktree. Scan JSON: each repository gains `interrupted`, and `summary` gains `interrupted_removals`.
- `remove --trash` moves each worktree into a trash instead of deleting it, and `--idle` turns it on, so a scheduled sweep is reversible; `--no-trash` deletes at once. Decision, where: `residue-trash/` in the repository's Git common directory (`.git/residue-trash/NAME-STAMP/`). A move there is one rename on the repository's filesystem, where linked worktrees usually live; every worktree of the repository finds it; `git status` never shows it; and it goes away with the repository. A worktree on another filesystem is refused, never copied. Each entry holds the worktree and a record, `info`, with its original path, branch, HEAD, time and size. The worktree stays registered and locked (`residue: in trash`), so restore and purge are Git commands; its branch stays checked out there until then.
- `residue restore` lists the trash of the repositories at or under the current directory; `residue restore ENTRY` (the entry name, the worktree's name or branch, or a path) moves it back with `git worktree move` and drops the entry. JSON schema `residue.restore/v1`.
- Every `remove` run purges the trash entries older than `--keep-trash DURATION` (default `7d`) in the repositories it covers, as part of the plan you confirm: each entry is checked again, without `--idle` (the trash's clock is `--keep-trash`), and deleted with `git worktree remove` without `--force`. The purge is what frees the disk, and the README says so. Remove JSON gains `trash` (`enabled`, `keep`, `keep_seconds`), `purged`, and `trash_entry` on each result; the result `trashed` is new. Scan JSON gains each repository's `trash` and `summary.trash_entries`. A sweep fails (exit 3) when an expired entry it meant to purge was skipped or failed, or a trash record could not be read; an entry kept because a check failed does not fail it.
- README: "The trash", and "Run it on a schedule" with `--keep-trash 7d` in the command, the launchd plist and the systemd service.
- JSON: each worktree's `rule_sources` is now its full effective list: `--regenerable` (`command_line`), the residue config file (`residue_config`), then its repository's Git config rules in the order Git reads them. Rules add up, so a duplicate applies once and its first entry is the source that wins. The top-level `rule_sources` stays the run-wide subset, now in the same order (`command_line` first). Before, a worktree listed only its Git config rules, so an agent judging one worktree had to merge two lists, and with Git config rules only, the top-level `[]` read as "no rules". The schemas stay at v1.
- `scripts/race-check.sh` drives the release binary's prompt under a pseudo-terminal, changes the worktree while the prompt waits (an untracked file, a modified tracked file, a file in an ignored regenerable directory, a new commit, with and without `--trash`), answers yes, and checks for exit 3, a `changed since you confirmed` reason, and the worktree still in place; two control cases must be removed or trashed. CI runs it on macOS and both Linux runners.
- Fix: a stale worktree in a sweep's `kept` list now says why it is stale.
- `residue watch ROOT...`: stays running and removes a worktree when its work landed (its upstream branch was deleted and it has been unchanged for `--grace`, default 1h) or when the disk is low (below `--min-free`, default 10%: worktrees unchanged for `--idle`, default 2d, largest first, until free space is 5 points above). No schedule: it wakes on changes under `refs/remotes`, `packed-refs` and `reftable` (inotify on Linux, kqueue on macOS and the BSDs), on the moment a waiting worktree passes its wait, and on a filesystem dropping below the threshold. Decision: `watch` deletes nothing itself. Every removal is a `residue remove --yes --idle --no-trash` child process, so it makes only removals `remove` would make. Decision, no trash: `--idle` turns the trash on, and `watch` turns it off, because freeing the disk is its job, a trashed worktree keeps every byte until a later run purges it, and nothing would purge the trash of a repository where `watch` removes nothing more. Each of its runs purges that repository's trash entries older than 7 days, and the log names each one. `--dry-run` logs instead, `--once` acts once. One `watch` per user (a lock in `$XDG_STATE_HOME/residue`).
- `residue service install|status|uninstall`: runs `residue watch` from login as a launchd agent on macOS or a systemd user service on Linux. Under Homebrew it starts the stable `bin/residue` link, so it survives `brew upgrade`.
- FreeBSD: an activity probe, from the base system's `procstat -f`. Before, FreeBSD had no probe, so nothing was ever a candidate. A packaged lsof is not used: on FreeBSD 14 it listed processes without resolving their working directories, so a worktree in use came back as a candidate. The procstat parser fails closed: a line it cannot read makes activity `unknown`.
- residue builds on illumos and Solaris, which have no `tm_gmtoff`. NetBSD, OpenBSD, DragonFly and illumos build but still have no probe, so nothing there is a candidate.
- CI runs `.github/smoke.sh` on macOS, Linux x86_64 and arm64, and FreeBSD 14 as root and as an ordinary user: a clean candidate, a kept `.env`, a worktree a process is using, and a removal that keeps the branch.
- Signed dnf and pacman repositories next to the apt one, at https://whiteheap.github.io/residue/rpm and https://whiteheap.github.io/residue/arch: `dnf install residue` on Fedora and RHEL, `pacman -S residue` on Arch and Omarchy, and `dnf upgrade` and `pacman -Syu` keep residue current. Every release updates all three. The `.rpm` files in the dnf repository are signed, and one key signs everything (`packaging/signing-key.asc`).

## 0.0.4 (2026-11-07)

Scheduled sweeps. A machine running agents all day leaked 44 worktrees (4.2 GB) in two days, so the plan was a daily unattended `residue remove`. The activity check cannot see a paused agent session: harnesses such as Claude Code reset the shell to the main checkout after every command, so a worktree whose agent is waiting for approval has no process inside it, and if its work is pushed it is a candidate. A person sees the plan before deleting; a scheduled run does not.

- `--idle DURATION` on `scan`, `explain` and `remove` (`30m`, `12h`, `2d`, `1w`; anything else, zero included, is a usage error). A worktree that changed within DURATION fails the new `idle` check, so it is `keep`, with a reason such as `changed 3 hours ago (--idle 2d)`. A last change residue cannot read makes the check `unknown`, which keeps it too. The check is reported right after `activity`. Without `--idle` it does not run, and every 0.0.3 verdict and check is unchanged.
- Decision, what counts as a change: the newest of (1) every entry the walk reaches in the checkout, ignored output included, (2) the files directly in the worktree's Git directory (`index`, `HEAD`, `ORIG_HEAD`, `FETCH_HEAD`, `COMMIT_EDITMSG`), and (3) the timestamp inside the newest HEAD reflog entry. The walk already reads every entry, so (1) costs nothing; it now also records which entry is newest. (2) catches `add`, `commit`, `checkout`, `reset`, `stash` and `fetch` when no file changed. (3) catches commits and checkouts by the time Git recorded. Not the mtime of `logs/HEAD`: measured with Git 2.50.1 and 2.43.0, `git gc` in the main checkout rewrites every linked worktree's `logs/HEAD` even when nothing expires, so its mtime would keep leaked worktrees in an active repository forever. Not the branch tip's commit time: a branch checked out in a worktree moves only through that worktree, so the reflog and index already record it, and a commit made elsewhere can be older than the checkout that brought it in. Not ctime (`touch`, `tar` and `rsync -a` set mtime on purpose) and not atime (backups and code search read every file). Reads leave no trace: measured on both Git versions, `git status`, `git diff` and `git log` on a settled worktree write nothing, and residue's own Git commands run with optional locks off, so a scan never resets the clock. The README tells people to lock a worktree that may sit without writes for longer than the idle time. Keeping a worktree that is still in use costs disk until the next run; removing one costs a paused agent its working directory, so the signal errs toward keep.
- `residue remove --all PATH...` treats each PATH as a scan root and removes every candidate under it, with the same plan, re-check and `git worktree remove` without `--force`. Decision: `remove --all --yes` is a usage error without `--idle`, because an unattended sweep without it is exactly the case above. `remove` without `--all` still takes only worktree paths, so a typo cannot turn into a sweep. A sweep exits 0 when every candidate was removed (or there was none) and 3 when a candidate was skipped or failed or part of a PATH could not be read; the worktrees it keeps are listed under `kept (N):` and do not fail it. The remove JSON gains `errors`.
- `explain` shows `last change` with the entry that set it (`index in its Git directory`, `src/main.rs in the worktree`, `HEAD reflog: commit: fix login`), replacing `newest change on disk`. The `changed N ago` fact in `scan` uses the same time. Every JSON document gains `idle` (threshold and seconds, or null); each worktree gains `last_change` (`unix`, `at`, `source`, `what`) and `last_change_error`. `size.newest_mtime` stays.
- README: "Run it on a schedule", with a launchd LaunchAgent and a systemd user service and timer for a daily 04:00 sweep, how to preview the next run, why `--idle` matters, and `git worktree lock` for sessions that may pause longer.
- Fix: rules from Git config named the wrong source. A rule from the global config (`~/.gitconfig` or `GIT_CONFIG_GLOBAL`) was reported as `This repository's git config residue.regenerable adds: ".env"`, so a reader looked in `.git/config` while the rule applied to every repository. residue now reads the key with `git config --show-scope --show-origin` and names each group of rules by scope and file: `global config (~/.gitconfig) adds ".env"; this repository's config (~/src/app/.git/config) adds "web/.tscache"`. An invalid value names its file too. In JSON, each worktree gains `rule_sources` (`rule`, `scope`, `origin`) for its Git config rules, and each document gains a top-level `rule_sources` for the residue config file (`residue_config`) and `--regenerable` (`command_line`). `regenerable_config` is unchanged: it is still the path of the residue config file, or null when there is none, and the schemas stay at v1.
- Fix: times named no zone. The header said `as of 00:23:02` in local time while `explain` said `2026-11-06 22:23 UTC`. Text output now uses local time with its UTC offset everywhere (`as of 00:23:02 +02:00`, `2026-11-07 00:23 +02:00`). JSON stays RFC 3339 UTC.
- Fix: run from `/`, as launchd and systemd start a job, residue printed every path relative to `/`, without its leading slash (`private/tmp/...`). Paths are now absolute there.
- README: regenerable rules apply only to ignored entries. An untracked file that is not ignored always blocks, and `--regenerable` does not change that.
- A signed apt repository for Debian and Ubuntu at https://whiteheap.github.io/residue/apt, so `sudo apt install residue` works and `apt upgrade` keeps residue current. It holds the latest release for amd64 and arm64, and every release updates it.

## 0.0.3 (2026-11-07)

Feedback from running 0.0.2 on an agent monorepo: a user set `residue.regenerable` through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>`, the environment form of `git -c`, and residue ignored it without a word.

- Decision: residue still ignores `residue.regenerable` set through the environment (`git -c` and `--config-env`, which Git passes on as `GIT_CONFIG_PARAMETERS`; `GIT_CONFIG_COUNT` with its pairs; the legacy `GIT_CONFIG`). Every subprocess and CI step inherits the environment, so it must not widen what residue deletes. `--regenerable` is the explicit rule for one run, and Git config files are the deliberate rule for a repository.
- It no longer ignores them silently. When the environment sets the key, residue prints a note on stderr naming the values, and points at `--regenerable` and `git config --add residue.regenerable`. Every JSON document gains `ignored_environment_rules`: the ignored values, an empty list when there are none, or null when Git could not read that environment (for example `GIT_CONFIG_COUNT=1` with no `GIT_CONFIG_KEY_0`). Git parses the variables itself, so quoting and key case follow Git. The schemas stay at v1. residue runs no extra Git process when none of the variables is set.
- Fix: 0.0.2 did not remove the legacy `GIT_CONFIG` variable. It makes `git config` read one file in place of every config file, so an inherited `GIT_CONFIG` replaced the repository's own rules, and a file it named with `residue.regenerable = .env` made a worktree holding `.env` a `candidate`. residue now removes `GIT_CONFIG` from its Git commands and reports the values in that file as ignored. It has no effect on other Git commands.
- `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM` are unchanged and documented: they choose which config files Git reads, and residue reads the same files as your Git. A user who relocates the global config keeps its `residue.regenerable` rules, as in 0.0.2. `GIT_CONFIG_NOSYSTEM` skips the system file.
- `--help` and the README say which sources count. AGENTS.md: after each release, upgrade this machine's Homebrew install.
- Linux packages on every release, for x86_64 and arm64: `.deb` for Debian and Ubuntu, `.rpm` for Fedora and RHEL, and a pacman package for Arch and Omarchy. Each is attested and listed in `SHA256SUMS`. v0.0.2 has them too.
- `packaging/aur/PKGBUILD` for the `residue-bin` AUR package.

## 0.0.2 (2026-11-06)

Feedback from running 0.0.1 on a busy agent monorepo: every worktree there held `.local-dev/` lock files, `.cargo/config.toml` and `web/.tscache/`, so nothing was a candidate unless each user added those names to a config file that then applied to every repository.

- Rules per repository from Git config: `git config --add residue.regenerable RULE`. residue reads them with `git config --get-all` in each worktree. An invalid value makes the `ignored` check `unknown` and names the value. It does not stop the scan. `explain` lists the values. residue never reads rules from a file committed to the repository, because a cloned repository must not be able to declare your files disposable.
- Path rules: a rule with a slash is a path from the worktree root (`web/.tscache`, `.local-dev/*.lock`). `*` matches within one segment. A path rule matches that entry and everything below it. Path rules work in the config file, `--regenerable` and Git config. Name rules are unchanged.
- Git reports a fully ignored directory once, as `dir/`. When a path rule reaches inside one, residue judges each file in it during the walk it already makes. The directory is regenerable only if a rule matches every file in it. `explain` names the first file that no rule matches. Above 100,000 entries, the directory is kept.
- Ignored entries show their file count and apparent size in the `scan` line, in `explain` (up to 8 entries), and on the `deletes ignored:` line of the `remove` plan, for example `ignored: .local-dev/ (2 files, 0 B), .vercel/ (2 files, 1.2 KB) (+5 more; 7 entries hold 31 files, 3.1 MB)`. Each hard-linked file counts once. JSON `ignored[]` entries gain `files` and `bytes` (null when not measured). The schemas stay at v1.
- The same walk sizes the ignored entries, judges collapsed directories and runs the safety checks. `git status` now runs before the walk. The order of the checks in the report is unchanged.
- Snapshot time: the text output of `scan`, `explain` and `remove` starts with `as of HH:MM:SS` in local time. Every JSON document has `generated_at` in RFC 3339 UTC. `explain` text now starts with the same header line as `scan`.
- `remove` still inspects each worktree twice, once for the plan and once right before deletion. Measured on macOS 26.3.1 (Apple silicon) with a 1.0 GB worktree of 46,572 entries (a pnpm `node_modules` and a Cargo `target`), over three rounds: `residue explain` took 0.65 to 0.83 s, `git worktree remove` of an identical copy took 2.69 to 3.04 s, and `residue remove --yes` took 3.68 to 4.34 s. The plan inspection is 13 to 22% of `remove --yes` (about 17% on average), under the 20% bar for removing it under `--yes`, so `remove` is unchanged.
- README: the `results[].result` values, a scan as a snapshot, `.vercel/` as a common non-regenerable entry, rules and their sources, the cost of the walk, and the platforms that ran 0.0.2.

## 0.0.1 (2026-11-06)

First release.

- `residue scan [PATH...]` lists the linked worktrees of each repository at or under PATH, with size, a verdict (`candidate`, `keep`, `unknown`, `stale`) and the reason for it.
- `residue explain PATH` shows every check for one worktree, and facts that never block: local-only commits, a gone upstream, the newest change on disk, and size.
- `residue remove PATH...` prints a plan, asks for confirmation (or accepts `--yes`), re-checks against a fresh process snapshot, then runs `git worktree remove` without `--force`. Branches and commits are kept.
- Activity probe with three states (`in_use`, `not_observed`, `unknown`): `lsof` on macOS, `/proc` on Linux.
- Ignored files block removal unless every one matches the regenerable list. Extend the list with `~/.config/residue/regenerable` or `--regenerable`.
- `--json` output for every command: `residue.scan/v1`, `residue.explain/v1`, `residue.remove/v1`.
