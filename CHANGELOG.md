# Changelog

## 0.0.8 (2026-11-08)

- `scan` prints a recovery line that works for every interrupted removal (#49). A run killed during the delete can leave a worktree under its hidden name that Git can no longer use, because its `.git` file or its HEAD is gone. Git refuses to move that worktree, but `scan` still printed `put it back: git worktree unlock ... && git worktree move ...`. Now it prints only the restore of its record: `Git can no longer use it (its .git file is gone), so it cannot move it back; restore says what to clear, then recreates it: residue restore RECORD`. The JSON `recovery` is that `residue restore RECORD`, or empty when no record names the worktree; it never deletes anything (AGENTS.md invariant). `interrupted` entries gain `unusable` (null, or why Git can no longer use it) and `removal_record` (the record's path, or null). `residue restore` also gives the steps for a worktree that lost its `.git` file, which it reported only as Git's `validation failed`, and its list says why Git can no longer use one.
- `residue restore` and `residue restore NAME` never search the whole home folder (#49). Run from the home folder or a folder above it, they look only in the usual code folders that exist in it, the ones `watch` uses (`~/src`, `~/Work` and the rest), and say which. When the name is in none of them, the message names the folders it searched and says to run the command inside the repository or to pass the record's path. When no code folder exists, both exit 1 and say so. Below the home folder nothing changes. Decision: search the code folders rather than refuse. A removal by `watch` with no ROOT is always in one of them, so `residue restore fix-login` from a new terminal, which opens in the home folder, finds it; a refusal would fail that common case. Before, the search read every folder under the home folder, and on macOS that asks for permission to Documents, Desktop and Downloads. #36 had guarded only a path ENTRY.
- Tests (#49): `scripts/recovery-check.sh` checks `scan`'s text and `recovery` for a worktree that lost its HEAD, adds a case for one that lost its `.git` file (`remove-fails-part-way-dotgit`), through to the restore, and one for a restore while the run that left it still runs (`remove-fails-part-way-running`): restore says to wait for that process and run it again, or, if the PID belongs to another process after a reboot, what to clear, where it printed `put it back with:` and an empty command. `scripts/contract-check.sh` adds `restore-name-from-home`. Each fails on `main` before this change.
- Install (#30): one command installs residue and, on macOS and Linux, turns on automatic cleanup: `curl -fsSL https://residue.whiteheap.com/install.sh | sh`. The script (`site/public/install.sh`, POSIX sh) uses Homebrew on macOS, the signed apt, dnf or pacman repository on Linux when it can act as root, and otherwise the release archive, checked against `SHA256SUMS` and, when `gh` is logged in, its build-provenance attestation; it pins the SHA-256 of the signing key it adds. Then it runs `residue service install`, leaves an existing service alone, and prints what it did and how to undo it. `--no-service`, `--archive`, `--prefix`, `--version` and `--dry-run`. Running it again upgrades. CI runs it through Homebrew, apt, dnf, pacman and the archive (macOS, Ubuntu, Alpine, FreeBSD). README and `docs/installation.md` lead with it; Homebrew and the manual channels remain.
- Install (#52): right after a release, when its FreeBSD archives are still being built, the script installs the newest release that has this machine's archive, names both versions and says to run it again later; before, it stopped with `curl: (22) ... 404`. It decides by the release's `SHA256SUMS` and finds the earlier release with one GitHub API call; when that call fails, it says the archive is still being built and how to pick a release with `--version`. `--version` stays exact: a release with no archive for this machine is a plain error, never another release.
- How much space residue freed (#38). A `remove` that deletes or moves something ends with one line: `freed about 812 MB (residue has freed about 14.2 GB on this machine since 2026-10-02)`, or for a move into the trash `moved about 812 MB to the trash, freed once a remove run purges it after 7d (...)`. A preview, or a run that removes nothing, prints none. `scan` at a terminal ends with the total and the last seven days once anything was freed. The `watch` log adds `freed about ...` after each removal, with the UTC date, like the log's own times. On macOS and Linux, `service status` has a `freed:` line: what automatic cleanup freed in the last seven days and when it last removed a worktree. A new command, `residue stats [--json]`, shows all time, the last 30 and 7 days, each by command (`remove`, a sweep, `watch`), by repository, the trash (moved there, and in it now) and restores; the JSON adds twelve weekly totals.
- Decision (#38), a ledger per user, `ledger.jsonl`: `~/Library/Application Support/residue/` on macOS, whatever `XDG_STATE_HOME` says, so a terminal, the launchd agent and an app read one file; elsewhere `$XDG_STATE_HOME/residue/` when it is an absolute path, else `~/.local/state/residue/`. The folder is mode 0700, the file 0600. One JSON line per event (`freed`, `trashed`, `restored`), appended with one `write(2)` under `O_APPEND` once the deletion, move or restore succeeded, so runs at the same time never overwrite each other's lines on a local filesystem (NFS does not promise it). A line residue cannot read is skipped and counted, and each event counts once, by repository and entry. An append to a file whose last line was cut short starts on a line of its own, so only the cut line is lost. residue reads and writes the ledger only as a regular file, opened without waiting: a FIFO, a device or a folder at its path is a warning, never a command that waits forever. A time outside 1970 to 9999 is read as the nearest end. Each size is the `reclaimable` estimate the removal record keeps; APFS snapshots, clones and hard links can keep some of the space. A move into the trash is not freed until its purge, and a restore does not subtract. Nothing in it leaves the machine (AGENTS.md invariant). Not the removal records alone: `--keep-removed` forgets them and a restore takes them back, so a total read from them would shrink.
- The ledger never affects a removal (AGENTS.md invariant): nothing reads it to decide anything, and a ledger residue cannot read or write is a warning, `residue: warning: the stats ledger is not up to date (...); this does not change what was removed`, on stderr, in `warnings` and in `stats.error`, never in `errors` and never in the exit status. `restore` adds it to its notes.
- Seeding (#38): before it acts, a `remove` that will delete or move something, `restore`, and `scan` without `--json` add what the ledger lacks from the removal records and trash entries of the repositories they read, as lines marked `"seeded": true`: removals by 0.0.7, which wrote removal records and no ledger, a ledger that could not be written, and a run stopped between the deletion and the append. Not seeded: records `--keep-removed` forgot or a restore took back, removals by 0.0.6 or earlier (which wrote no record), interrupted removals (nothing was deleted), and records whose run may still be going. `scan --json`, `explain` and `stats` never write the ledger.
- JSON, additive (#38): `remove` gains `stats`, its last field: `freed_bytes`, `freed_worktrees`, `trashed_bytes`, `trashed_worktrees`, `total_freed_bytes`, `total_freed_worktrees`, `since`, `ledger` and `error`. A ledger it could not write is also in `warnings`. New schema: `residue.stats/v1`, whose spans, twelve weeks and repositories each split by command (`by`: `remove`, `sweep`, `watch`, `other`), with the estimate sentence as `estimate_note`, for a client to show in residue's words. Scan, explain and restore documents are unchanged.
- Changes from 0.0.7 (#38): `stats` is now a command word, so `residue stats` no longer scans a folder named `stats`; `residue scan stats` does.

- Removal records in a reftable repository (#48): the reflog pins now keep two more kinds of commit the worktree's HEAD reflog held. One is the oldest entry's old value, which Git reads as `HEAD@{N}`: Git 2.50 to 2.56 expire every entry older than 30 days, so the commit before an amend or a rebase can end up there. The other is any commit the worktree's reflogs name that the main worktree's do not, such as one whose own entry, the one that moved HEAD to it, `git gc` expired or `git reflog delete` took. Before, residue read only each entry's new value, and after the removal `git gc` deleted those commits. Decision: residue does not pin such an old value when another reflog, such as a branch's, also names it. No Git command prints it, so residue cannot tell it from that reflog's own history; that reflog keeps it until `git branch -D` or `git stash drop` deletes the reflog, or it expires; and pinning every commit any reflog names would pin other branches' history in each record (AGENTS.md invariant). `residue restore` there now says that it did not put the HEAD reflog back, and why, on stderr and in `restore.notes`; before, a restore that pinned nothing dropped the record without a word. `docs/platforms-and-testing.md` records the swapped expiry defaults and the command that re-checks them. Tests: `scripts/contract-check.sh` gains `record-reflog-reftable-expired` and `record-reflog-reftable-deleted`, and `record-reflog-reftable` checks the note; each fails on 0.0.7.

- Restore after `git refs migrate` (#58): a worktree removed while the repository kept its refs in files and restored after `git refs migrate --ref-format=reftable` lost the commits only its HEAD reflog held. Restore wrote the saved reflog to `logs/HEAD`, a file Git does not read in a reftable repository, then read that same file back to decide the worktree held those commits, so it dropped the record and its reflog refs, and the next `git gc` deleted the commits. Restore now goes by how the repository keeps its refs when restore runs, not when the record was written. In reftable it writes no `logs/HEAD`, says `its HEAD reflog was not put back` on stderr and in `restore.notes`, and keeps a record that holds a saved reflog, with its refs, until `--keep-removed`. Before it drops any record, it asks Git which commits the restored worktree's HEAD reflog names (`git rev-list --walk-reflogs HEAD` and `--single-worktree --reflog`), never the file. A record from a reftable removal restored after a migration back to files stays, as before. A removal in reftable no longer copies or reads a `logs/HEAD` file it finds there, such as the one an earlier restore wrote after the migration: Git does not read it, and residue read it in place of Git's reflog, so commits made in the restored worktree went unpinned. Tests: `scripts/contract-check.sh` gains `record-reflog-migrated`, both directions, skipped on a Git without `git refs migrate`, which came in 2.46, and `record-reflog-reftable-stray`; both fail on 2c8a36d, where `git gc --prune=now` lost the commit after the migration and the removal copied the stray file.

## 0.0.7 (2026-11-08)

- Automatic cleanup in one command (#28): `residue service install` and `residue watch` take no ROOT. Without one they use the usual code folders in the home folder that exist: `~/src`, `~/code`, `~/Code`, `~/dev`, `~/Developer`, `~/projects`, `~/Projects`, `~/repos`, `~/git`, `~/github`, `~/GitHub`, `~/work`, `~/Work` and `~/workspace`, each once (on a case-insensitive filesystem `~/code` and `~/Code` are one folder), and print which. Never the home folder itself, which holds far more than code, and nothing under `Documents`, `Desktop` or `Downloads`, which macOS guards with a permission prompt a background service cannot answer. When none exists, both print one line that names the folders and how to pass a ROOT, and exit 2. A ROOT replaces the list. `service install` never prompts, so an installer can run it, and prints the folders and `residue service uninstall` to turn it off.
- `service install` writes the resolved roots into the service, so it watches the same folders at every start, and marks them as the default ones. `service status` now shows what the service runs (`runs:`) and which folders it watches (`watches:`). Running `service install` again replaces the service: without a ROOT it keeps the ROOTs a user named for the service it replaces, dropping any that is no longer a folder, with a note, and a service on the default folders looks for them again, which picks up a folder created since. Options are not kept: each one not given goes back to its default, and the command says so when the service it replaced was a `--dry-run`. The Homebrew formula defines no service. If a Homebrew service for residue exists anyway, from a formula of the user's own, `service install` says so and exits 1, since only one `watch` runs per user, and `service status` points to `brew services info residue`.
- Decision (#28), `watch` fetches. Until now residue never fetched, so `watch` saw a landed branch only after the user's own `git fetch --prune`, and an automatic cleanup could wait for one indefinitely. `watch` now runs `git fetch --prune --no-tags` for each repository about every 30 minutes (`--fetch-every DURATION`; each repository on its own clock, its interval varied by up to a tenth). It fetches only the remotes that a linked worktree's branch tracks, and nothing in a repository with no such branch, since no other ref decides anything `watch` does. It fetches in the main checkout with `--no-write-fetch-head`, `--no-auto-maintenance` and `--no-recurse-submodules`, so no file in a worktree's Git directory, which is the idle clock, changes. It never waits for a person: a new session with no terminal, `GIT_TERMINAL_PROMPT=0`, `SSH_ASKPASS_REQUIRE=never`, `GCM_INTERACTIVE=never`, and SSH `BatchMode=yes` unless the user set `GIT_SSH_COMMAND`, `GIT_SSH` or `core.sshCommand`, which is used as it is; and a five-minute deadline, after which the fetch and every program it started (SSH) are killed. A fetch only refreshes the remote-tracking refs that the scan and the removal read: it is never itself a reason to remove, every check still decides, and a failed fetch logs one line (once, until it changes or works again) and leaves that repository's refs as they were. A branch the fetch finds deleted is logged before any removal it leads to. `--no-fetch` turns it off; `--dry-run` still fetches. `scan`, `explain` and `remove` never fetch, so the removal child's three upstream reads stay local. The AGENTS.md invariants record this.
- Upgrading: a service installed by 0.0.6 or earlier carries neither `--fetch-every` nor `--no-fetch`, so after the upgrade it fetches every 30 minutes. To keep the old behavior, install it again with `--no-fetch` and its ROOTs.
- `residue scan` at a terminal ends with one line when automatic cleanup is off, that is when no `residue service` or Homebrew service is installed and no `watch` of this user is running: `Automatic cleanup is off. Turn it on: residue service install`, with the scanned PATHs added when the default folders do not hold every repository it listed. Only on macOS and Linux, only when it lists linked worktrees, never in a pipe or with `--json`; the JSON schema is unchanged.
- `residue scan --json` (#45): each repository's `free_space` has `device`, the filesystem's device number (`st_dev`) as a decimal string, so a reader can show one free-space figure per disk, as `watch` decides per disk. A string, since a device number can exceed 2^53, past what a JavaScript number holds exactly. It groups repositories within one document only: it changes across reboots and mounts, so never store it or compare it across runs. The schema stays `residue.scan/v1`.
- A child process that overruns its deadline and leads its own process group, as the fetch does, is killed with its group.
- Decision (#31), every deletion is restorable. Until now only `remove --trash` could be undone; a worktree that `remove`, `--no-trash`, `watch` or the trash purge deleted was gone, and its HEAD commit was safe only while a branch or reflog held it. Now each of them first writes a removal record, `residue-removed/ENTRY/info` in the repository's Git common directory (the path, branch, HEAD, upstream, why, by which command (`by remove`, `by sweep`, `by watch`; a purge names the run that purged), when, the size and the ignored entries the deletion took, plus copies of the worktree's HEAD reflog and `config.worktree`), and a ref, `refs/residue/removed/ENTRY`, at that HEAD, so a deleted branch, an expired reflog or `git gc` cannot lose the commit. A removal writes them after the move aside and before its check at the new path, and drops them when that check fails; the purge writes them after its re-check. Both write them before `git worktree remove`; if any of it cannot be written, it deletes nothing (`could not write its removal record, so residue deleted nothing`, result `skipped`, exit 3; a purge keeps the entry in the trash). `info` is written under another name, synced and renamed into place, the record's directories are synced, and the refs are written in one `git update-ref --stdin` transaction with `core.fsync=reference` and `core.fsyncMethod=fsync` (Git 2.36 adds `reference` to its platform default; macOS's default method only writes out), so a crash leaves all of it or none.
- Decision (#31), commits only the worktree's own reflog held are kept. `git worktree remove` deletes the worktree's Git directory and its HEAD reflog with it. A commit made on a detached HEAD and then checked out away from, or the commit before an amend or a rebase, could have that reflog as its only holder, so `git gc` deleted it after the removal although every check passed. Now the record pins those commits: one ref each, `refs/residue/reflog/ENTRY/N`, at the fewest commits that reach all of them (`git merge-base --independent` over every commit the reflog names, as an old or a new value, that no ref outside `refs/residue/` and no worktree's HEAD reaches). Another reflog naming such a commit does not count as a holder: a branch's reflog goes with `git branch -D`, and reflogs expire. A reftable repository (Git 2.45 and later) has no `logs/HEAD` file to read or copy; there residue asks Git for the commits that reflog names (`git rev-list --walk-reflogs HEAD`, each entry's new value) and pins those, and since restore cannot write that reflog back, the record stays until `--keep-removed`. The worktree's private refs (`refs/worktree/`, `refs/bisect/`, `refs/rewritten/`) and an operation in progress already keep it from removal, so the reflog is all its Git directory adds. Removal does not wait on this; it pins and goes on. The invariant, in AGENTS.md: while a record lives, nothing residue removes, restores or forgets makes such a commit unreachable.
- What `--keep-removed` can lose: once a record is forgotten, a commit only its refs held is left to `git gc`. That is the commits of a branch deleted after the removal, for example after a squash merge, and of work only the worktree's reflog held. For those, `--keep-removed` (30 days) is the only grace period. The README says so. Decision, a ref and not a branch: a branch would show in `git branch`, could be checked out, pushed or deleted by the user's own tools, and its name could collide; `refs/residue/` is residue's alone. `git log --all` and `git push --mirror` see it.
- `residue restore` lists trash entries and removal records together, newest first, with their kind and why they went, and `residue restore ENTRY` recreates a removed worktree with `git worktree add` at its path, never `--force`: on its branch when the branch is at the recorded HEAD or ahead of it; as `BRANCH-restored` at the recorded HEAD when the branch was rewritten, which stays as it is; on the branch created again when it was deleted; detached when it was. A branch checked out in another worktree, or anything at the path, refuses; `--to PATH` restores somewhere else. The ignored files the deletion took, such as `node_modules/`, are listed as not kept. A removal that did not finish, whose worktree Git still lists under its hidden name, is listed as `interrupted`, and restore moves it back; when Git deleted that worktree's HEAD reflog or `config.worktree`, restore puts the saved ones back, and when Git can no longer use it, restore says to delete it and run `git worktree prune`, after which the same restore recreates it. A recreated worktree gets the saved HEAD reflog back, in front of its new one. Then restore drops the record and its refs, whether it recreated the worktree or moved it back, but only once the worktree's HEAD contains the recorded HEAD and its own HEAD reflog names every pinned commit; when it could not put back the saved `config.worktree` or reflog, or a branch moved while it ran, the record stays, and restore says where and why. An ENTRY path is looked up from the nearest folder above it that exists, and when that finds no entry, from the current directory; but never from the home folder or a folder above it, which would read every folder in it (on macOS, a permission prompt for Documents, Desktop and Downloads): restore asks to be run inside the repository instead.
- Every `remove` run forgets the removal records older than `--keep-removed DURATION` (default `30d`) in the repositories it covers, in the plan you confirm: the record and its refs, in one transaction, only while each still names the commit the record names; with any other ref under its name, or one that moved, the record and its refs stay. `watch`'s child uses the default. A directory with no `info` and no ref, left by a run stopped while it wrote one (nothing was deleted then), is cleared once it is an hour old.
- A removal record residue cannot read or forget never fails a removal: `remove` reports it on stderr (`residue: warning: ...`) and in a new JSON array, `warnings`, and the exit status says only whether the PATHs and the trash went. `errors` keeps its meaning: what residue could not read about the PATHs, the repositories and the trash. `watch` logs both. Otherwise one damaged record would have made every later `remove` in its repository exit 3, against "exit 3 means it is still there".
- A deletion that fails after Git deleted part of the worktree keeps its record. `git worktree remove` deletes the files, then Git's directory for the worktree, entry by entry in the order the filesystem lists them, and stops at the first one it cannot delete; so it can fail with the worktree still listed and its files, its HEAD reflog, its `config.worktree`, its HEAD or its `commondir` gone. residue undid the record whenever the files were still there, so after a failure in Git's directory it moved the worktree back without the reflog and dropped the refs that kept the commits only that reflog held, and `git gc` deleted them. Now it undoes the record only while nothing of the worktree is gone: Git lists it and can still use it, its files and `.git` file are there, its HEAD contains the recorded HEAD, its `logs/HEAD` still begins with the saved copy and its `config.worktree` is the saved copy. Otherwise the worktree stays under its hidden name, never moved back, and the failure names the record (`Git still lists it at PATH, but part of its HEAD reflog is gone; its removal record keeps its HEAD and reflog: residue restore RECORD`). The purge does the same.
- Entry names are unique across the trash and the removal records: both are `NAME-STAMP`, and a new one skips a name the other kind has. Restore's JSON reads `worktree_config` and `head_reflog` from the record as it was listed, not from the live files.

## 0.0.5 (2026-11-07)

Deletes what you saw, or nothing, and makes a scheduled sweep reversible. Until 0.0.4, `remove` re-ran the checks right before acting, but it compared the verdict, HEAD, branch, lock and the set of ignored entries, not what they held. Measured with `scripts/race-check.sh` against the 0.0.4 release binary: a file added inside `node_modules/` while the prompt waited was deleted with the worktree (exit 0). And a scheduled sweep that took a paused agent's worktree took it for good.

- Decision, the plan is a record: for each worktree it now keeps HEAD, the branch, the lock, the staged, modified and untracked files, the file count, size and newest modification time of every ignored entry, and the modification times of the worktree's `index` and `logs/HEAD`. Right before acting, residue compares a fresh record with it and skips on any difference, with a reason that names the difference: `node_modules/ changed since you confirmed (1,204 -> 1,388 files)`, `HEAD changed since you confirmed (a82c15ee7687 -> 55c48105f23a)`, `changed since you confirmed: 1 untracked`. Under `--yes` the reason says `since the plan`. `logs/HEAD` is fine here although `--idle` must not use it: a `git gc` between plan and removal only makes residue skip.
- Decision, move aside before deleting: after the re-check, `git worktree move` renames the worktree to a hidden sibling, `.NAME.residue-removing-PID`, and residue locks it with the reason `residue: removing`. `git worktree move` is one rename by Git that updates only this worktree's record, and it refuses another filesystem instead of copying; residue skips a worktree that is a mount point. Not `mv` plus `git worktree repair`: `repair` rewrites the records of every worktree of the repository. At the new path residue checks again: Git lists it there with the planned HEAD, branch and residue's lock, a new process snapshot sees nobody inside it, and the record still matches. Then it unlocks it and `git worktree remove`, without `--force`, deletes it. On any difference or failure it moves the worktree back and unlocks it (`...; it is back in place`). This narrows the window between the last check and the deletion; it does not close it. From that check until Git finishes, a process that opens the hidden directory by its new name, or one the probe cannot see, can still write into it, and the write is deleted with it. The README says so.
- A run killed partway leaves the worktree under its hidden name, still registered. `scan` lists it under `interrupted removals` with the one command that puts it back (`git -C MAIN worktree unlock HIDDEN && git -C MAIN worktree move HIDDEN ORIGINAL`, or `git worktree remove HIDDEN` when the directory is gone), and says when the PID that moved it still runs. Neither a sweep nor `remove PATH` touches such a worktree. Scan JSON: each repository gains `interrupted`, and `summary` gains `interrupted_removals`.
- `remove --trash` moves each worktree into a trash instead of deleting it, and `--idle` turns it on, so a scheduled sweep is reversible; `--no-trash` deletes at once. Decision, where: `residue-trash/` in the repository's Git common directory (`.git/residue-trash/NAME-STAMP/`). A move there is one rename on the repository's filesystem, where linked worktrees usually live; every worktree of the repository finds it; `git status` never shows it; and it goes away with the repository. A worktree on another filesystem is refused, never copied. Each entry holds the worktree and a record, `info`, with its original path, branch, HEAD, time and size. The worktree stays registered and locked (`residue: in trash`), so restore and purge are Git commands; its branch stays checked out there until then.
- `residue restore` lists the trash of the repositories at or under the current directory; `residue restore ENTRY` (the entry name, the worktree's name or branch, or a path) moves it back with `git worktree move` and drops the entry. JSON schema `residue.restore/v1`.
- Every `remove` run purges the trash entries older than `--keep-trash DURATION` (default `7d`) in the repositories it covers, as part of the plan you confirm: each entry is checked again, without `--idle` (the trash's clock is `--keep-trash`), and deleted with `git worktree remove` without `--force`. The purge is what frees the disk, and the README says so. Remove JSON gains `trash` (`enabled`, `keep`, `keep_seconds`), `purged`, and `trash_entry` on each result; the result `trashed` is new. Scan JSON gains each repository's `trash` and `summary.trash_entries`. A sweep fails (exit 3) when an expired entry it meant to purge was skipped or failed, or a trash record could not be read; an entry kept because a check failed does not fail it.

Rules add up, so a duplicate applies once and its first entry is the source that wins. The top-level `rule_sources` stays the run-wide subset, now in the same order (`command_line` first). Before, a worktree listed only its Git config rules, so an agent judging one worktree had to merge two lists, and with Git config rules only, the top-level `[]` read as "no rules". ## 0.0.4 (2026-11-07)

Scheduled sweeps. A machine running agents all day leaked 44 worktrees (4.2 GB) in two days, so the plan was a daily unattended `residue remove`. A last change residue cannot read makes the check `unknown`, which keeps it too. The check is reported right after `activity`. Without `--idle` it does not run, and every 0.0.3 verdict and check is unchanged.
- Decision, what counts as a change: the newest of (1) every entry the walk reaches in the checkout, ignored output included, (2) the files directly in the worktree's Git directory (`index`, `HEAD`, `ORIG_HEAD`, `FETCH_HEAD`, `COMMIT_EDITMSG`), and (3) the timestamp inside the newest HEAD reflog entry. The walk already reads every entry, so (1) costs nothing; it now also records which entry is newest. (2) catches `add`, `commit`, `checkout`, `reset`, `stash` and `fetch` when no file changed. (3) catches commits and checkouts by the time Git recorded. Not the mtime of `logs/HEAD`: measured with Git 2.50.1 and 2.43.0, `git gc` in the main checkout rewrites every linked worktree's `logs/HEAD` even when nothing expires, so its mtime would keep leaked worktrees in an active repository forever. Not the branch tip's commit time: a branch checked out in a worktree moves only through that worktree, so the reflog and index already record it, and a commit made elsewhere can be older than the checkout that brought it in. Not ctime (`touch`, `tar` and `rsync -a` set mtime on purpose) and not atime (backups and code search read every file). Reads leave no trace: measured on both Git versions, `git status`, `git diff` and `git log` on a settled worktree write nothing, and residue's own Git commands run with optional locks off, so a scan never resets the clock. The README tells people to lock a worktree that may sit without writes for longer than the idle time. Keeping a worktree that is still in use costs disk until the next run; removing one costs a paused agent its working directory, so the signal errs toward keep.
- `residue remove --all PATH...` treats each PATH as a scan root and removes every candidate under it, with the same plan, re-check and `git worktree remove` without `--force`. Decision: `remove --all --yes` is a usage error without `--idle`, because an unattended sweep without it is exactly the case above. `remove` without `--all` still takes only worktree paths, so a typo cannot turn into a sweep. A sweep exits 0 when every candidate was removed (or there was none) and 3 when a candidate was skipped or failed or part of a PATH could not be read; the worktrees it keeps are listed under `kept (N):` and do not fail it. The remove JSON gains `errors`.
- `explain` shows `last change` with the entry that set it (`index in its Git directory`, `src/main.rs in the worktree`, `HEAD reflog: commit: fix login`), replacing `newest change on disk`. The `changed N ago` fact in `scan` uses the same time. Every JSON document gains `idle` (threshold and seconds, or null); each worktree gains `last_change` (`unix`, `at`, `source`, `what`) and `last_change_error`. `size.newest_mtime` stays.
- README: "Run it on a schedule", with a launchd LaunchAgent and a systemd user service and timer for a daily 04:00 sweep, how to preview the next run, why `--idle` matters, and `git worktree lock` for sessions that may pause longer.
- Fix: rules from Git config named the wrong source. A rule from the global config (`~/.gitconfig` or `GIT_CONFIG_GLOBAL`) was reported as `This repository's git config residue.regenerable adds: ".env"`, so a reader looked in `.git/config` while the rule applied to every repository. residue now reads the key with `git config --show-scope --show-origin` and names each group of rules by scope and file: `global config (~/.gitconfig) adds ".env"; this repository's config (~/src/app/.git/config) adds "web/.tscache"`. An invalid value names its file too. In JSON, each worktree gains `rule_sources` (`rule`, `scope`, `origin`) for its Git config rules, and each document gains a top-level `rule_sources` for the residue config file (`residue_config`) and `--regenerable` (`command_line`). `regenerable_config` is unchanged: it is still the path of the residue config file, or null when there is none, and the schemas stay at v1.
- Fix: times named no zone. The header said `as of 00:23:02` in local time while `explain` said `2026-11-06 22:23 UTC`. Text output now uses local time with its UTC offset everywhere (`as of 00:23:02 +02:00`, `2026-11-07 00:23 +02:00`). JSON stays RFC 3339 UTC.
- Fix: run from `/`, as launchd and systemd start a job, residue printed every path relative to `/`, without its leading slash (`private/tmp/...`). Paths are now absolute there.
- README: regenerable rules apply only to ignored entries. An untracked file that is not ignored always blocks, and `--regenerable` does not change that.
- A signed apt repository for Debian and Ubuntu at https://whiteheap.github.io/residue/apt, so `sudo apt install residue` works and `apt upgrade` keeps residue current. It holds the latest release for amd64 and arm64, and every release updates it.

## 0.0.3 (2026-11-07)

Feedback from running 0.0.2 on an agent monorepo: a user set `residue.regenerable` through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>`, the environment form of `git -c`, and residue ignored it without a word.

- Decision: residue still ignores `residue.regenerable` set through the environment (`git -c` and `--config-env`, which Git passes on as `GIT_CONFIG_PARAMETERS`; `GIT_CONFIG_COUNT` with its pairs; the legacy `GIT_CONFIG`). Every subprocess and CI step inherits the environment, so it must not widen what residue deletes. `--regenerable` is the explicit rule for one run, and Git config files are the deliberate rule for a repository.
- It no longer ignores them silently. When the environment sets the key, residue prints a note on stderr naming the values, and points at `--regenerable` and `git config --add residue.regenerable`. Every JSON document gains `ignored_environment_rules`: the ignored values, an empty list when there are none, or null when Git could not read that environment (for example `GIT_CONFIG_COUNT=1` with no `GIT_CONFIG_KEY_0`). Git parses the variables itself, so quoting and key case follow Git. The schemas stay at v1. residue runs no extra Git process when none of the variables is set.
- Fix: 0.0.2 did not remove the legacy `GIT_CONFIG` variable. It makes `git config` read one file in place of every config file, so an inherited `GIT_CONFIG` replaced the repository's own rules, and a file it named with `residue.regenerable = .env` made a worktree holding `.env` a `candidate`. residue now removes `GIT_CONFIG` from its Git commands and reports the values in that file as ignored. It has no effect on other Git commands.
- `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM` are unchanged and documented: they choose which config files Git reads, and residue reads the same files as your Git. A user who relocates the global config keeps its `residue.regenerable` rules, as in 0.0.2. `GIT_CONFIG_NOSYSTEM` skips the system file.
- `--help` and the README say which sources count. AGENTS.md: after each release, upgrade this machine's Homebrew install.
- Linux packages on every release, for x86_64 and arm64: `.deb` for Debian and Ubuntu, `.rpm` for Fedora and RHEL, and a pacman package for Arch and Omarchy. Each is attested and listed in `SHA256SUMS`. v0.0.2 has them too.
- `packaging/aur/PKGBUILD` for the `residue-bin` AUR package.

## 0.0.2 (2026-11-06)

Feedback from running 0.0.1 on a busy agent monorepo: every worktree there held `.local-dev/` lock files, `.cargo/config.toml` and `web/.tscache/`, so nothing was a candidate unless each user added those names to a config file that then applied to every repository.

- Rules per repository from Git config: `git config --add residue.regenerable RULE`. residue reads them with `git config --get-all` in each worktree. An invalid value makes the `ignored` check `unknown` and names the value. It does not stop the scan. `explain` lists the values. residue never reads rules from a file committed to the repository, because a cloned repository must not be able to declare your files disposable.
- Path rules: a rule with a slash is a path from the worktree root (`web/.tscache`, `.local-dev/*.lock`). `*` matches within one segment. A path rule matches that entry and everything below it. Path rules work in the config file, `--regenerable` and Git config. Name rules are unchanged.
- Git reports a fully ignored directory once, as `dir/`. When a path rule reaches inside one, residue judges each file in it during the walk it already makes. The directory is regenerable only if a rule matches every file in it. `explain` names the first file that no rule matches. Above 100,000 entries, the directory is kept.
- Ignored entries show their file count and apparent size in the `scan` line, in `explain` (up to 8 entries), and on the `deletes ignored:` line of the `remove` plan, for example `ignored: .local-dev/ (2 files, 0 B), .vercel/ (2 files, 1.2 KB) (+5 more; 7 entries hold 31 files, 3.1 MB)`. Each hard-linked file counts once. JSON `ignored[]` entries gain `files` and `bytes` (null when not measured). The schemas stay at v1.
- The same walk sizes the ignored entries, judges collapsed directories and runs the safety checks. `git status` now runs before the walk. The order of the checks in the report is unchanged.
- Snapshot time: the text output of `scan`, `explain` and `remove` starts with `as of HH:MM:SS` in local time. Every JSON document has `generated_at` in RFC 3339 UTC. `explain` text now starts with the same header line as `scan`.
- `remove` still inspects each worktree twice, once for the plan and once right before deletion. Measured on macOS 26.3.1 (Apple silicon) with a 1.0 GB worktree of 46,572 entries (a pnpm `node_modules` and a Cargo `target`), over three rounds: `residue explain` took 0.65 to 0.83 s, `git worktree remove` of an identical copy took 2.69 to 3.04 s, and `residue remove --yes` took 3.68 to 4.34 s. The plan inspection is 13 to 22% of `remove --yes` (about 17% on average), under the 20% bar for removing it under `--yes`, so `remove` is unchanged.
- README: the `results[].result` values, a scan as a snapshot, `.vercel/` as a common non-regenerable entry, rules and their sources, the cost of the walk, and the platforms that ran 0.0.2.

## 0.0.1 (2026-11-06)

First release.

- `residue scan [PATH...]` lists the linked worktrees of each repository at or under PATH, with size, a verdict (`candidate`, `keep`, `unknown`, `stale`) and the reason for it.
- `residue explain PATH` shows every check for one worktree, and facts that never block: local-only commits, a gone upstream, the newest change on disk, and size.
- `residue remove PATH...` prints a plan, asks for confirmation (or accepts `--yes`), re-checks against a fresh process snapshot, then runs `git worktree remove` without `--force`. Branches and commits are kept.
- Activity probe with three states (`in_use`, `not_observed`, `unknown`): `lsof` on macOS, `/proc` on Linux.
- Ignored files block removal unless every one matches the regenerable list. Extend the list with `~/.config/residue/regenerable` or `--regenerable`.
- `--json` output for every command: `residue.scan/v1`, `residue.explain/v1`, `residue.remove/v1`.
