# Changelog

## Unreleased

- **`residue service status` shows `watch`'s last pass, so a watch that waits no longer looks stuck** (#181). Two lines after `freed:`: when the last pass ended, how many worktrees it saw, how many were candidates, changed within `--grace` or kept, and by which checks (`22 kept (ignored 13, activity 7, untracked 2)`), the fullest disk's free space against `--min-free`, then what the next pass waits for: a branch that lands, with the next fetch, the disk dropping below `--min-free`, or a worktree passing `--grace` or `--idle`. A record more than seven hours old is marked stale, since a running `watch` passes at least every six hours; with none yet it says so. The log gets one `pass:` line whenever that summary changes, so a quiet day is short but never silent. A running `watch` (never `--once`) writes the record at the end of each pass, whole, as `watch-pass.json` beside the stats ledger; it decides nothing, and one that cannot be written or read is a log line or a status line, never a change to a pass, a removal or an exit status. [Is it working?](docs/automation.md#is-it-working) has the details.
- **For scripts and integrations:** `residue stats --json` adds `watch_pass`, the same record as fields, or null when no `watch` wrote one; `residue.stats/v1` is unchanged otherwise. `service status` keeps its first line, `fingerprint:` and `log:` lines as they were and adds `last pass: ...` and `next pass: ...` before `log:`. The `watch` log adds `pass: SUMMARY; logged again when this changes`, `cannot write the record of this pass, which service status shows (WHY); passes and removals go on as before` and `the record of each pass is written again`.
- **On APFS, the reclaimable and freed sizes leave out what a clone outside the worktree keeps.** A file made by `cp -c`, Finder's Duplicate or pnpm's install shares its blocks with another, and deleting it frees only the blocks it does not share. From macOS 11 the size walk asks macOS for that number for each such file, in the listing call it already makes or one call for the file through the folder it holds, and counts it toward `reclaimable` and the space `stats` records as freed. From macOS 14 a file and its full clone, both in the worktree, count once. A worktree whose `target/` was a `cp -c` clone of a 100 MiB folder kept elsewhere was "about 105 MB reclaimable" and freed 0.1 MiB; it is now about 12.3 KB. `watch`'s low-disk rule, which removes the largest candidates first, now picks by what a removal frees. `allocated` and `apparent` are unchanged. A block two worktrees share counts for neither, so removing both frees more than their sizes add up to, and Btrfs, XFS and ZFS clones are still not detected (#193).
- **On Linux, a `/proc` mounted with `hidepid=ptraceable` keeps activity `unknown` also when residue is in the mount's `gid=` group.** In that mode the kernel shows a process only to one who may ptrace it and never asks about `gid=`, so membership does not let residue see every process of yours. With the other `hidepid` values a member of `gid=` sees every process, as before.
- **`watch`'s fetch changes only the remote-tracking refs of the remote it fetches.** It now gives Git only that remote's fetch refspecs that store under `refs/remotes/` and not into another remote's `refs/remotes/OTHER/`, so tags, notes, other remotes' refs and every other ref stay as they are, whatever else the remote's refspecs, `fetch.pruneTags` or `remote.NAME.pruneTags` name. With remotes such as `origin` and `origin/fork`, one name inside the other, neither is fetched. A refspec with no `*` whose destination is a symbolic ref, such as one you pointed at a local branch, is left out too, since Git would store through it and move that branch. Your own `git fetch` is unchanged. A remote with nothing left is not fetched, and `watch` logs what it leaves out once.
- **The install script checks which workflow built the archive.** With `gh` installed and logged in, a release archive's build-provenance attestation must come from the workflow that builds it, at its ref, on a GitHub-hosted runner: `release.yml` at the release's tag for macOS and Linux, `packages.yml` on `main` for FreeBSD. Before, an attestation from any workflow in the repository passed. The summary names what it checked. A `gh` older than 2.49 stops the script with a message to update it, instead of gh's own error. The release notes and `docs/installation.md` give the same check by hand.
- **On Arch, residue's package database must be signed.** The `[residue]` section the install script and the manual steps write sets `SigLevel = Required DatabaseRequired`; pacman's default accepts an unsigned database. The script also adds that line to a `[residue]` section an older script or the manual steps wrote without one, once `pacman-conf` shows that pacman would read every other `SigLevel` as before. It writes `/etc/pacman.conf` beside itself and renames it into place, so a full disk leaves it as it was, and keeps the file as it was in `/etc/pacman.conf.residue-bak` (`.residue-bak.1` and so on beside an older one). A `SigLevel` you set yourself, two `[residue]` sections, a section in an included file and a linked `/etc/pacman.conf` with a section to edit are left as they are, with a note. A `[residue]` line followed by a comment, which pacman does not read as a section, and an `/etc/pacman.conf` the script cannot read stop it before it changes anything.
- **For scripts and integrations:** `watch` logs, once until it changes, `fetch of REMOTE in PATH leaves out REFSPEC (remote OTHER's refs)` or `REFSPEC (its destination is a symbolic ref)` for a refspec it leaves out, and `not fetching REMOTE in PATH: WHY; its refs stay as they were; next try in about DURATION` for a remote it does not fetch, where WHY is `none of its fetch refspecs stores into refs/remotes/`, `each of its fetch refspecs into refs/remotes/ also stores into another remote's refs: REFSPEC (remote OTHER's refs)`, or, when one of them was left out for a symbolic destination, `each of its fetch refspecs into refs/remotes/ is left out: ` and the same list.
- **A trash entry keeps its own `--keep-trash`.** `remove --trash` writes the `--keep-trash` it ran with into the entry's record, and no later run purges the entry sooner: a sweep or `watch` with the default `7d`, or a run with `--keep-trash 1d`, keeps an entry trashed with `30d` for thirty days, as a removal record keeps its `--keep-removed`. An entry an earlier release made is purged as before. `residue restore --json` shows it as `keep` and `keep_seconds`.
- **The purge keeps the record of what it leaves.** When a trash entry holds a file residue did not put there, beside the worktree and its record, the purge still deletes the worktree, keeps the entry's record with that file, and says so in a warning.
- **A trash entry no purge can act on is kept, with a warning, instead of failing every run.** That is an entry whose worktree is gone but that still holds something else, one with no record that holds anything, which an earlier release could leave, one that holds its worktree while Git lists that worktree somewhere else, and one whose `keep` line this release cannot read, which stays restorable. The warning names what the entry holds, or the `git worktree repair` that reconnects it. Once what it holds is moved or deleted, a later run clears it. A restore that leaves such an entry names what it holds. An entry whose record is damaged or cannot be read still fails the run, as before.
- **A bare repository's trash is judged as its worktrees are.** An entry on the branch the bare repository's HEAD names is kept, as that branch's worktree is, instead of planned as a purge and then skipped by every run.
- **The purge writes its removal record before its last check,** as a removal does, so writing and syncing the record is not part of the time between that check and the deletion. A change that check finds keeps the entry, and undoes the record unless the change took something the record keeps, such as a commit `git reset` moved HEAD off; then the record stays and the run names it. A purge first forgets the record an earlier purge of the same entry left without deleting anything, when the worktree still holds all it keeps; otherwise it keeps the entry until you restore it, naming that record, so it never records one worktree twice. A record it cannot read that may be such a purge's keeps the entry too, with a warning naming it, and is never forgotten.
- **A confirmed plan removes only what it showed.** `residue remove --json` reports the plan's fingerprint, `plan`. Given it, `remove --yes --expect PLAN` makes its own plan before it moves anything and, when that is another one, removes, trashes, purges and forgets nothing and exits 4: a worktree at a PATH moved to another branch or HEAD, another worktree took its path, or a trash entry or removal record the plan did not list would go. So a program that shows a plan, such as the Mac app, can have residue remove only what you confirmed, where before the second run removed the candidate it found at each PATH, whichever worktree that was (#184).
- **On macOS, a process of yours that lsof cannot see keeps activity `unknown`.** lsof leaves out, with no error, every process it may not inspect, such as each process of yours outside a sandbox that residue runs in. residue now lists every process before lsof runs and looks up each one lsof did not list, or listed without reading every file of it (`FD info error`). One that runs as your user, or whose user residue cannot read, makes activity `unknown` (`probe_failed`), which keeps the worktree, and the reason names it: `lsof did not list 534 running processes of yours, such as zsh[25712]: a sandbox around residue may hide them`. A process that exited meanwhile, or another user's, does not count. Run residue outside the sandbox to judge the worktree.
- **Where residue cannot see every process of yours, it keeps the worktree.** Inside a container (a PID namespace of its own), in a user namespace of its own (toolbx, distrobox) or under a `/proc` mounted with `hidepid` on Linux, in a jail, or beside jails it may not see into (`security.bsd.see_jail_proc` at 0) on FreeBSD, or in a non-global zone on illumos, a process outside can be using a worktree residue cannot see. A worktree with no use found there is now `unknown` (`hidden_processes`), so nothing there is removed on activity grounds: `residue runs inside a container (a PID namespace of its own), so it cannot see processes outside it`. A use residue does see is still `in_use`. Run residue on the host to judge such a worktree. A WSL distribution, which runs in a PID namespace of its own and holds your whole Linux session, is judged as any Linux once residue sees WSL's `/init` in its `/proc`; a container on WSL's kernel, as Docker Desktop runs one, and a sandbox started in a distribution are still containers.
- **On Linux, a process of yours that the kernel will not show residue keeps activity `unknown`** (`probe_failed`), and the reason names it, as on FreeBSD: one started with another of your groups (`sg`, `newgrp`, `docker run --user UID:GID`), or one outside a Landlock sandbox around residue. One that changes its user as residue reads it (cron, sshd, su) is read again and does not count. A process that is not dumpable, such as ssh-agent, or that holds a capability you lack, such as systemd's user manager on some systems, is still not inspected: the kernel shows those only to root.

  - A trash entry's JSON (`restore --json`, a scan's `trash`, and `purged[].entry`) gains `keep` and `keep_seconds`, null for an entry 0.0.13 or earlier made. The entry's `info` gains a `keep SECONDS DURATION` line, which 0.0.5 to 0.0.13 ignore.
  - An expired entry on the branch a bare repository's HEAD names is `purged[].result` `kept`, its `head` check blocking, not `skipped`. So is one whose worktree Git lists somewhere else, which was `failed` with exit 3.
  - `purged[].removal_record` also names the record a purge leaves when it did not delete the worktree, instead of null.
  - The help's exit status line names a trash entry that could not be purged, as the reference does.
  - `residue.remove/v1` adds `plan`, 32 lowercase hex digits, in every remove document, and `expected_plan`, the `--expect` PLAN or null, both after `stats`, and `repository` on each result, its repository's common Git directory, or null for a PATH that names no worktree (#184).
  - `remove --yes --expect PLAN` is new. When the run's plan is not PLAN, it exits 4, and each result, trash entry and removal record it would have acted on is `skipped`, with a `reason` that starts `the plan is not the one --expect names`. Its text ends `nothing removed: the plan is not the one --expect names; something changed since that plan was made`, then `next: if this plan is the one to run, run again with --expect PLAN` (#184).
  - `--expect` outside `remove` and `service install`, and `remove --expect` without `--yes`, without a PLAN, given twice or with a PLAN that is not 32 lowercase hex digits, exit 2. `service install --expect` is unchanged (#184).
  - A text plan with something to confirm, and one under `--expect`, ends with `plan: PLAN` before the prompt or the results. The help's exit status line names 4 (#184).
  - On macOS 11 and later, `reclaimable_bytes`, `candidate_reclaimable_bytes`, the removal record's `reclaimable` and the bytes `stats` and the ledger count as freed leave out the blocks a file shares with an APFS clone outside the worktree (#193). No field is new; `allocated_bytes` and `apparent_bytes` are unchanged.
  - On macOS, when lsof did not list a running process of yours, the JSON `activity` header has `"available": false`, `"reason": "probe_failed"` and that `detail`, and each worktree's `activity` is `unknown` with the same reason and detail. No field is new.
  - In a container, a jail, a non-global zone or under `hidepid`, a worktree's `activity.reason` is the new value `hidden_processes`, the JSON `activity` header stays `"available": true`, and the header's text ends with where residue runs (`procfs inspected 4 of 4 running processes, inside a container`).
- **A folder or file mounted a second time inside a worktree keeps it.** On Linux and illumos, a bind mount or a loopback (lofs) mount from the worktree's own filesystem is now a `mount_point`, at the plan and in the check after the move aside, as a mount of another filesystem always was. Elsewhere a file mounted over a file, as FreeBSD's nullfs can, is one too.

### Details

- `git::fetch` reads every remote's config in one `git config --null --get-regexp '^remote\.'` and passes, after the remote's name, each of its refspecs whose destination is under `refs/remotes/` and can name no ref under another remote's `refs/remotes/OTHER/` (with a `*`, when the part before it and `refs/remotes/OTHER/` start the same way, one the other), and each negative one, in their order, with `--refmap=` and `--no-prune-tags`. Git then writes and prunes only those destinations. Git prunes no symbolic ref and stores nothing through one for a refspec with a `*` (`ignore_symref_update`), but it does for a refspec with no `*`, so `git::symbolic_destinations` leaves out each such refspec whose destination `git symbolic-ref -q` reads as a symbolic ref. The fetch no longer sets `refs/remotes/NAME/HEAD`, which Git does only when no refspec is given, and it runs with `remote.NAME.followRemoteHEAD=never` (through `GIT_CONFIG_COUNT`) for Git 2.48 and later; residue reads no such ref. Each fetch of a remote runs one more `git config`. Tests: `git::tests` (which refspecs are kept, both ways round for nested remote names, reading the remotes from Git's config, and when a remote is not fetched) and `.github/watch-smoke.sh` case 12.
- Release pipeline: `packages.yml` builds packages only from Linux archives `release.yml` attested at the tag, uploads only the files it builds, by exact name, keeps `release.yml`'s `SHA256SUMS` lines, attests and uploads only from `main`, and builds the FreeBSD archives from the tag, never a branch of that name. Its `repositories` job signs only packages `packages.yml` attested on `main`. Signing happens on the runner; `repo-add` runs in `archlinux:base` pinned by digest with no key and no network (`packaging/arch-repo.sh`, `packaging/repositories.sh`). A dry run also builds and checks the three repositories with a key made for the run. The site deploys with the Wrangler that `site/package-lock.json` pins, installed with `npm ci --ignore-scripts`, and pull requests run it as a dry run. Tests: `.github/workflows/install.yml` checks the identity each archive is verified against (`release.yml` at the tag, the old name for 0.0.5, `packages.yml` on `main` for FreeBSD) and the pacman section's `SigLevel`. From a section an older script wrote, `.github/pacman-siglevel-check.sh` shows the dry run naming the change, the line added once with nothing else changed, the backup, a second run changing nothing, an older backup kept with the next one at `.residue-bak.1`, a `SigLevel` of the user's own, two sections, an `Include` and a linked file each left alone with a note, a header followed by a comment stopping the script on the stock Arch layout, every other repository's `SigLevel` unchanged there, pacman refusing an unsigned database it took before, and, with `/etc` on a full tmpfs, the edit and a fresh install stopping with `pacman.conf` as it was and nothing left behind.
- `fsinfo::Mounts`: the walk tells each entry's mount, not only its device. On Linux it lists each entry with statx(2) and compares its mount ID (`STATX_MNT_ID`, Linux 5.8 and later) with the worktree folder's, and counts an entry statx marks as a mount's root (`STATX_ATTR_MOUNT_ROOT`). Where statx gives no mount ID (before Linux 5.8, a seccomp filter that refuses it, qemu-user before 11, which gives 0), and on illumos, it takes each mount point `/proc/self/mountinfo` or `/etc/mnttab` lists inside the worktree. On illumos it also counts each entry with the device and inode of the source of a lofs mount on the worktree's device, which it looks up from `/` without following a link (and the mount point, where the source does not lead to that device), so a lofs mount the table names by a path renamed since, or one seen through another lofs mount, counts too. It reads the table again after the walk. One statx probe per process decides whether statx is there, and any error there means it is not; after a probe that worked, any statx error is that entry's read error. Everywhere but Linux, a file on another device counts as a folder does. Where the walk needs the table and cannot read it, a line of `/etc/mnttab` has other than five fields, neither lookup of such a lofs mount leads to its device, or a mount came during the walk, `contents` is `unknown`: `cannot tell whether it holds a mount point: REASON`, and after the move, `cannot tell whether it holds a mount point after residue moved it aside: REASON`. The `mount_point` detail ends `removal could delete what is mounted there`, in place of `removal could delete files on another filesystem`. Tests: `fsinfo::tests`, and `scripts/recovery-check.sh` 2e to 2e4 as root (a bind mount on Linux, nullfs on FreeBSD, lofs on illumos), which CI now also runs as root on Linux, and on `ubuntu-24.04` again with statx refused (`.github/nostatx.c`).
- `remove --expect`: `remove::plan_of` reads the plan right after it is made, before the prompt, the stats seed or any move, and `fingerprint::plan` hashes it with `fingerprint::Hasher`, the FNV-1a 128-bit hash over parts with their lengths that `service install --expect` uses. The two now share it, and the service's fingerprint is unchanged. Each worktree counts by its canonical path, its common Git directory and what the plan does with it, and, when it removes or trashes it, its branch and HEAD as Git lists them; each trash entry by its path, what the plan does with it and, when it purges or clears it, its record and Git's branch and HEAD for the worktree in it; each removal record by its path, what the plan does with it and, when it forgets it, its record and the commits its refs keep; and the plan's `--keep-trash` and `--keep-removed`. The steps are sorted and each counted once, so the order of the PATHs does not count. No time, size, process, reason or state of a worktree the plan keeps counts, so two runs with nothing changed agree. Tests: `fingerprint::tests`, `cli::tests`, `service::tests::fingerprint_is_unchanged`, and in `scripts/contract-check.sh` the `usage-expect-*` cases and section 19: a plan confirmed with its PATHs in the other order, a branch switched, a HEAD moved, another repository's worktree at the PATH, and an expired trash entry that appears after the plan, each exit 4 with nothing removed, moved aside, trashed, purged or forgotten, the plan that run reported confirmed in turn, and a worktree the plan keeps whose branch changed (#184).
- `activity::unlisted` (macOS): `proc_listallpids` before lsof runs; then, for each pid lsof did not print, `proc_pidinfo(PROC_PIDT_SHORTBSDINFO)` and, where a sandbox refuses it, the `kern.proc.pid.PID` sysctl; a process lsof listed with a name in place of a file (`FD info error`) is looked up the same way; one of yours still missing or unread is asked of lsof again (`-p`), since lsof can miss a process launchd is starting. `scripts/contract-check.sh` sections 20 and 20b, `activity-sandboxed` and `activity-sandboxed-files`, run residue under `sandbox-exec` while a process outside the sandbox works in the worktree, or holds a file there.
- `activity::Seen::hidden`, set by `activity::procview` (Linux: `/proc/self/ns/pid` against `PROC_PID_INIT_INO`, the `NSpid` count, `/proc/self/ns/user` against `PROC_USER_INIT_INO`, except in a WSL distribution (`procview::wsl`: `osrelease` names Microsoft, WSL's `/init` in the `/proc` residue reads, and none of `procview::CONTAINER_MARKERS`), and the `/proc` mount's `hidepid` and `gid=` in `/proc/self/mountinfo` unless residue holds `CAP_SYS_PTRACE` in the initial user namespace), `activity::jailed` and `activity::jails_hidden` (FreeBSD: `security.jail.jailed`; `security.bsd.see_jail_proc` with a jail from jail_get(2)) and `activity::in_zone` (illumos: `getzoneid()`). On Linux, `platform::yours` and `procview::refusal` fail the probe for a process whose `/proc/PID/status` has your effective user as owner but whose `fd` or `maps` answers Permission denied, unless its `CapPrm` holds a capability residue's `CapEff` lacks, and name the check that refused (user ids, group, or a sandbox or security module). `scripts/contained-check.sh` runs residue in a PID namespace (`unshare --pid --fork`, with and without `--mount-proc`), a user namespace, an emulated WSL 2 distribution and a sandbox in it, under a `/proc` with `hidepid`, or in a jail, as root, in CI on the Ubuntu runners and in the FreeBSD machine; `scripts/contract-check.sh` section 21, `activity-other-group`, starts a holder with `sg`.

## 0.0.13 (2026-11-09)

Automatic cleanup on macOS and the BSDs no longer stops for good when `watch` runs out of open files, and a worktree with an ignored entry residue could not measure is kept.

- **A running `watch` on macOS and the BSDs no longer runs out of open files.** kqueue holds an open file for each folder `watch` watches, and launchd starts a service with a limit of 256. With many branch folders under `refs/remotes`, the watches took them all, and every pass after that failed with `could not start: Too many open files`, so automatic cleanup stopped and removed nothing. `watch` now raises its limit on open files and keeps 128 of it free for the Git and residue each pass starts (#168).
- **On macOS, residue spells each name in a path as Git does.** Git precomposes each name on its own and keeps a name it cannot convert, such as one with an emoji, as stored. residue now does the same, name by name, so its walk measures an ignored folder below such names (#172).
- **An ignored entry the walk did not reach is not judged.** A rule that matches it no longer makes it regenerable: the `ignored` check is `unknown` (`the walk did not reach it`), which keeps the worktree (#172).
- **For scripts and integrations (changed from 0.0.12):** such an entry is `"regenerable": false`, with `files` and `bytes` null as before, and the `ignored` check's `status` is `unknown` (#172).

### Details

- `Events::room` (kqueue): the soft `RLIMIT_NOFILE` is raised toward the hard limit, at most 10,240 (`OPEN_MAX` on macOS), and the watches stop 128 below it, as well as at `MAX_WATCHES`. inotify watches hold no open file and are unchanged. Tests: `events::tests` and `.github/watch-smoke.sh` scenario 11, a running watch under `ulimit -n 256` with 302 folders to watch, which removes a worktree whose upstream is pruned.
- `fsinfo::git_path` converts each name that holds a non-ASCII byte with Apple's `iconv` from UTF-8-MAC to UTF-8 on its own, keeps a name the conversion refuses or leaves alone, and gives the path as bytes, so the bucket lookup matches Git's path byte for byte. `inspect::judge` calls an entry `unknown` when the walk did not reach it or could not run, before the environment-file check. Tests: `fsinfo::tests::each_name_is_spelled_on_its_own_and_a_refused_one_is_kept`, `fsinfo::tests::git_spells_a_path_name_by_name_with_apples_converter` and `fsinfo::tests::a_bucket_in_gits_spelling_is_found_below_a_refused_name` (macOS), `inspect::tests::an_ignored_entry_the_walk_did_not_reach_is_not_judged`, and `scripts/contract-check.sh` section 12b, `ignored-mixed-names-env`, `ignored-mixed-names-env-swapped` and `ignored-mixed-names-clean` (macOS; skipped by name elsewhere).

## 0.0.12 (2026-11-09)

Launch hardening: residue keeps more worktrees that are in use or hold what it cannot rebuild, stops on a mistyped command or an old Git before anything runs, replaces only the service you looked at, and comes with a skill for coding agents.

- **An `.env` inside a build folder is kept.** An environment file inside an ignored directory a rule matches, such as `build/.env` or `dist/.env.production`, now keeps its worktree, as an ignored `.env` at the top always has: `ignored: build/.env`. Templates (`.env.example`) and files in `node_modules` and virtual environments do not count, and a rule naming the file itself (`git config --add residue.regenerable build/.env`) lets residue delete it (#158).
- **A bare repository's HEAD branch is kept.** In the layout `git clone --bare` and then a `git worktree add` per branch makes, the worktree on the branch the bare repository's HEAD names is its main checkout in all but name. The `head` check now blocks it: `on main, the branch the bare repository's HEAD names; kept like a main checkout` (#156).
- **`residue service uninstall` and `status` take no arguments.** `residue service uninstall --dry-run` uninstalled the service; now any argument but `--help` is a usage error and nothing runs (#156).
- **A mistyped command is a usage error.** `residue clean` printed `could not inspect: clean: No such file or directory` and exited 0; now it says `residue: clean is not a command, and there is no folder named clean here; commands: scan, explain, remove, restore, stats, watch, service` (#156).
- **`residue` in the home folder scans the usual code folders**, as `restore` does, and says which; it no longer walks the whole home folder. A PATH, `~` included, is scanned as given (#156).
- **An old Git stops `service install` and `watch --once` before they start**, and the install script before it adds a package repository or asks for a password. A running `watch` says so once and waits for a newer Git, instead of failing every pass (#156).
- **`service install` and the install script say what automatic cleanup removes**, that it deletes without the trash and for how long `residue restore` brings a worktree back, and how to preview it (#156).
- **A skill for coding agents.** `npx skills add whiteheap/residue-cli --skill residue -g` gives Claude Code, Codex and other agents the steps to remove the worktree they created once a task is done, and what to do when residue keeps it (`skills/residue/SKILL.md`, #163).
- **`service install --expect` replaces only the service you looked at.** `residue service status` prints a fingerprint of the service. Given it, `install` writes nothing and exits 4 when the service changed since, so the Mac app can no longer save over a change a terminal or `brew upgrade` made while its dialog was open. Installs and uninstalls now run one at a time (#162).
- **A process in a worktree keeps it in use whatever characters its path has,** such as é, 漢字, an emoji or a backslash, in the worktree's name or a folder above it. On macOS, residue now matches the names lsof prints escaped. Where it cannot be sure how lsof prints a path, activity is `unknown`, which keeps the worktree. On FreeBSD, residue reads each process's working directory, executable and open files from the kernel (`kern.proc.filedesc`), byte for byte, instead of from procstat (#157).
- **On illumos, an open file whose path the kernel cannot give still keeps its worktree in use:** residue finds the file by its inode. Where it cannot look, activity is `unknown`, and the detail names the process. A deleted file does not count (#160).
- **A worktree that holds a very long path is kept.** Each probe names a path whole only below a length: 1,004 bytes on macOS, 4,096 on Linux and 1,024 elsewhere. A worktree with a path that long anywhere inside it is now `unknown` (`long_path`), so it is never a candidate, and says how long that path is. So is one whose paths would reach that length where residue deletes it, at its hidden name or in the trash, so the plan never lists a worktree that the check after the move then keeps (#165).

## 0.0.10 (2026-11-08)

Removal and restore that stay safe when a worktree, or another residue run, changes under them, and less CPU and memory.

- **Nothing that turns up after the move is deleted.** `remove` refuses a repository, a mounted volume or a folder it cannot read that appears in a worktree after residue moves it aside, and puts the worktree back (#106). A folder named `.git` in another case, such as `private/.GIT/`, keeps the worktree (#102). The size walk never follows a symbolic link, also one swapped in while it reads (#94).
- **Restore and its records tell the truth.** A removal record whose worktree is back reads `back`, `watch` no longer removes that worktree again because its work landed, and `residue restore` of it finishes what an earlier restore left (#99). A restore racing a forget of the same record keeps the commits only its reflog held (#98), and a trash entry can no longer get stuck (#97).
- **Less CPU and memory.** residue notices that a Git call has finished as soon as it exits (#82), on macOS each Git call starts sooner (#81), and `git status` uses a third to a half of the system CPU it did (#75). `explain` of a large worktree spends about half as long in `git status` (#83) and uses about 5 MB less memory (#78). On macOS no child process inherits another child's pipes, in residue (#114) and in the Mac app (#116). The Mac app uses less CPU and memory (#75, #95), and its text is brief (#77).
- **On macOS**, an ignored folder whose name the disk stores decomposed gets its size (#103), and `explain` run from inside a worktree no longer names lsof as a process using it (#85). **On Linux**, the activity check sees a process that uses a worktree only through a mapped file (#84).
- **Changes from 0.0.9.** A removal record's `state` in `--json` can now be `back`, `unknown`, `incomplete` or `unreadable`, so a record that did not plainly remove its worktree never reads `removed` (#99). On Linux, a worktree that a process uses only through a mapped file is kept as in use (#84). On NetBSD, OpenBSD and DragonFly, and on macOS 12 and earlier, every folder above a worktree must be readable, not only searchable (#94). `--help` and result lines are shorter; JSON documents, exit statuses and the lines the Mac app reads are unchanged (#77).

### Details

- A removal record whose worktree is back no longer reads as removed, and `watch` no longer removes that worktree again because its work landed. Back means Git lists a worktree with its checkout at the record's original path on its branch (detached when the record is), at the recorded HEAD or ahead of it: what a restore that kept its record leaves, or one stopped after `git worktree add` before it wrote its restored marker, or a `git worktree add` there by hand, or a run that moved the worktree back and could not drop the record. A locked worktree whose folder is gone is not back. Its `state` is now `back`; seeding adds no `freed` line for it; `watch`'s landed rule keeps the worktree while the record lives, as it keeps a marked one; and `residue restore` of it, without `--to`, finishes the job: it writes the restored marker if there is none, puts back the saved `config.worktree` (next to the worktree's own when that one differs), and puts the saved HEAD reflog in front of the worktree's own, then drops the record once the worktree holds what its refs keep (`checkout` `already_back`). Before, a restore stopped after `git worktree add` left the commits only the old reflog held to `git gc` once the record was forgotten. In a reftable repository Git cannot take the old reflog back, so the record stays and the restore says why. When Git cannot compare the worktree's HEAD with the recorded one, the `state` is `unknown`, with `back_error` saying why, never `removed`: seeding adds nothing, `watch` keeps the worktree, and restore of it without `--to` refuses. A record with no `info` now reads `incomplete` and one residue cannot read `unreadable`, with their `incomplete` and `error` fields as before. Decision: new `state` values rather than new fields, so a script that reads only `state` never sees `removed` for a worktree that is back or for a record that deleted nothing; the Mac app's types take the new values, and it offers Restore only for `removed`, `interrupted` and `back`, and no `freed` size for a worktree that is back. A trash restore that lands while a purge deletes the same entry no longer makes the purge say "Git no longer lists it, so part of it may be gone": the purge also looks for the worktree at its original path, and when Git lists it there whole, the purge is `skipped`, says another run put it back, and drops its record. A worktree at a listed path counts as the record's only when its Git directory is the one the record was written for, the same directory and not one Git made again under its name, so another worktree added at that path never makes the purge drop the record and the refs that keep the trashed worktree's commits. Dropping a record another run already dropped is no longer an error. The removal child reads no records, so a worktree that is back is kept by `watch`'s own filter, not by the child's `--only-if-upstream-gone` check. Tests: `scripts/recovery-check.sh` adds `purge-restore-race` (a purge held at `git worktree remove` while `residue restore` moves the worktree out of the trash), `restore-stopped-before-mark` (a restore killed at its first Git command in the worktree it recreated, then run again), `purge-other-worktree` and its reftable run (a purge's remove that stops part way while another worktree sits at the original path), `back-locked-missing` and `back-unknown`; `.github/watch-smoke.sh` adds step 9 (that worktree, its upstream gone, past `--grace`). `purge-restore-race`, `restore-stopped-before-mark`, `back-unknown` and step 9 fail on 0.0.9; the other three guard this change's own matching (#99).
- `remove` no longer deletes a repository or a mounted volume that appears in a worktree after residue moves it aside. The check after the move compared only what the plan recorded. `git status` lists neither a `.git` inside a folder Git tracks nor anything under an ignored folder, so a `git init` in `src/`, or a volume mounted under `node_modules/`, passed that check. `git worktree remove` then deleted the repository with its commits, or the files on the volume. A folder nobody can read passed too, and the removal stopped part way. Now the check after the move refuses what the check before it refuses: a `.git` entry other than the worktree's own, a mount point, or an entry residue cannot read. The reason says what it found and where, such as `contains a .git entry at src/.git after residue moved it aside; it is back in place`, and the worktree is moved back. Tests: `scripts/recovery-check.sh` adds `nested-repo-after-move`, `mount-after-move` and `unreadable-after-move`, which plant each one between the plan and that check. All three fail on 0.0.9. `mount-after-move` mounts a disk image on macOS, and a tmpfs as root on Linux, FreeBSD and illumos; it is skipped elsewhere. `unreadable-after-move` is skipped as root, who can read any folder (#106).
- On macOS, a child process residue starts, such as Git, no longer inherits the pipes of another child started at the same moment. The standard library makes a child's pipes and marks them close-on-exec in two steps, and residue inspects up to 8 worktrees at once, so a Git process started on one thread between the two steps held another's output open: that call ended only when the other process, and anything it left running, exited. Now one child starts at a time, and the lock is held for the start alone. Through residue's own process code, 335 of 48,000 children started on 8 threads had inherited a pipe before, and none now. A `scan` of 10 worktrees takes as long and uses as much CPU as before. This also fixes a test that failed now and then under load (#114, #111).
- On macOS, a child process the Mac app starts, such as residue, no longer inherits the pipes of another child the app started at the same moment, the race #114 found in residue's own children. The window's requests run on several threads, so a quick one, such as reading the Automatic cleanup status, could wait until an unrelated `scan` ended. Now the app also starts one child at a time, holding the lock for the start alone, and `app/src-tauri/clippy.toml` refuses any other way to start one. Through the app's own process code, 844 of 48,000 children started on 8 threads had inherited a pipe before, and none now. Starting them took no longer (#116).
- A worktree holding a folder named `.git` in another case, such as `private/.GIT/`, is now kept. On macOS Git's `core.ignorecase` is on, so Git skips that name in any case and `git status` lists nothing inside it. residue matched only `.git`, so it saw no ignored files and no nested repository, and could remove the worktree with that folder's files unlisted. The `nested_repo` check now blocks on any case of `.git` at any level, other than the worktree's own `.git` link. That includes a `.GIT/` at the root, which a case-sensitive file system can hold beside the link: a repository made on macOS and copied to Linux keeps `core.ignorecase` on. The check names the entry it found: `contains a .git entry at private/.GIT: another repository or checkout, or files Git does not list`. Where Git is case-sensitive and lists such a folder's files, residue keeps the worktree when it need not, the safe direction for a name this rare (#102).
- A restore and a forget of the same removal record at the same time no longer lose the commits only its reflog held without saying so. When a `remove` run, such as a `watch` child, forgot a record past `--keep-removed` while `residue restore` recreated its worktree, restore found the saved reflog gone and put none back. Then it said the record stayed "with its refs, so nothing it keeps is lost", though the record and its refs were gone and `git gc` could drop those commits. Now restore reads the record's copies before it changes anything, so it puts the reflog back from them. A record forgotten before that read makes restore change nothing, exit 1, and say another run took it. Whether the record stays is said from its refs as Git has them then; when another run forgot it and the reflog could not go back (a reftable repository), restore names each commit no ref keeps any more. Tests: `scripts/recovery-check.sh` adds `restore-forget-race` (the restore held at `git worktree add` while a sweep forgets the record), `forget-restore-race` (the sweep held at its ref deletion while the restore finishes first; its forget fails, as a warning), `forget-before-restore-reads` and `restore-forget-race-reftable`. - On macOS, an ignored folder whose name is stored decomposed on disk, such as `café/` written as `cafe` and a combining accent, now gets its size, and a path rule inside it can match. Git prints such a name precomposed, so residue never found the folder: it reported no size, and a rule like `café/sub/*.txt` kept the worktree with "the walk did not reach it". residue now also looks each non-ASCII path up the way Git spells it, with the same conversion Git uses (`iconv` from UTF-8-MAC), and matches a rule against either spelling. - A trash entry can no longer get stuck. A `remove` run in the same repository, such as the Mac app's or a `watch` child's, cleared an entry that held only its record at once, also one another run had just made and was moving a worktree into; that worktree could land in the trash with no `info`, so `residue restore` could not take it and every later `remove` there exited 3. Tests: `scripts/recovery-check.sh` adds `trash-move-in-flight` (a second run purges while the first is held at its move into the trash) and `scripts/contract-check.sh` adds `trash-record-only`; both fail on 0.0.9. A move that lands between the purge's own two steps, removing `info` and then the folder, is not something the Git wrapper can hold; the hour is what keeps a purge from reaching it (#97).

It opened each folder by its full path, so a folder, or one above it, that became a symbolic link during the walk was followed, and the sizes and the `nested_repo`, `mount_point` and `contents` checks described another tree. Now it opens each folder from the one above it with `O_NOFOLLOW` and checks that it is the folder the listing showed; a change makes `contents` `unknown`. With a folder swapped for a link to another tree over and over, `explain` read that tree in 12 of 400 runs before this change and in none of 300 after it, which reported `contents` `unknown` in 8. A walk holds at most 22 descriptors at any depth, 176 for `scan`'s 8 workers. It is no slower: `explain` of a 98,466-entry worktree took 0.68 to 0.81 s, against 0.70 to 0.98 s, with 0.50 to 0.61 s of system CPU against 0.51 to 0.76 s and the same memory, and of a tree 41 folders deep ending in 3,000 folders 0.26 to 0.29 s, against 0.27 to 0.29 s. On NetBSD, OpenBSD and DragonFly, and on macOS 12 and earlier, every folder above the worktree must now be readable, not only searchable (#94).
- Shorter output: `--help` gives one line per command and option, then examples, and result lines and caveats say the same in fewer words. JSON documents, exit statuses and the lines the Mac app reads are unchanged (part of #77).

Until now residue never fetched, so `watch` saw a landed branch only after the user's own `git fetch --prune`, and an automatic cleanup could wait for one indefinitely. `watch` now runs `git fetch --prune --no-tags` for each repository about every 30 minutes (`--fetch-every DURATION`; each repository on its own clock, its interval varied by up to a tenth). It fetches only the remotes that a linked worktree's branch tracks, and nothing in a repository with no such branch, since no other ref decides anything `watch` does. It fetches in the main checkout with `--no-write-fetch-head`, `--no-auto-maintenance` and `--no-recurse-submodules`, so no file in a worktree's Git directory, which is the idle clock, changes. It never waits for a person: a new session with no terminal, `GIT_TERMINAL_PROMPT=0`, `SSH_ASKPASS_REQUIRE=never`, `GCM_INTERACTIVE=never`, and SSH `BatchMode=yes` unless the user set `GIT_SSH_COMMAND`, `GIT_SSH` or `core.sshCommand`, which is used as it is; and a five-minute deadline, after which the fetch and every program it started (SSH) are killed. A fetch only refreshes the remote-tracking refs that the scan and the removal read: it is never itself a reason to remove, every check still decides, and a failed fetch logs one line (once, until it changes or works again) and leaves that repository's refs as they were. A branch the fetch finds deleted is logged before any removal it leads to. `--no-fetch` turns it off; `--dry-run` still fetches. `scan`, `explain` and `remove` never fetch, so the removal child's three upstream reads stay local. The AGENTS.md invariants record this.
- Upgrading: a service installed by 0.0.6 or earlier carries neither `--fetch-every` nor `--no-fetch`, so after the upgrade it fetches every 30 minutes. To keep the old behavior, install it again with `--no-fetch` and its ROOTs.
- `residue scan` at a terminal ends with one line when automatic cleanup is off, that is when no `residue service` or Homebrew service is installed and no `watch` of this user is running: `Automatic cleanup is off. Turn it on: residue service install`, with the scanned PATHs added when the default folders do not hold every repository it listed. Only on macOS and Linux, only when it lists linked worktrees, never in a pipe or with `--json`; the JSON schema is unchanged.

A string, since a device number can exceed 2^53, past what a JavaScript number holds exactly. - A child process that overruns its deadline and leads its own process group, as the fetch does, is killed with its group.
- Decision (#31), every deletion is restorable. Until now only `remove --trash` could be undone; a worktree that `remove`, `--no-trash`, `watch` or the trash purge deleted was gone, and its HEAD commit was safe only while a branch or reflog held it. Now each of them first writes a removal record, `residue-removed/ENTRY/info` in the repository's Git common directory (the path, branch, HEAD, upstream, why, by which command (`by remove`, `by sweep`, `by watch`; a purge names the run that purged), when, the size and the ignored entries the deletion took, plus copies of the worktree's HEAD reflog and `config.worktree`), and a ref, `refs/residue/removed/ENTRY`, at that HEAD, so a deleted branch, an expired reflog or `git gc` cannot lose the commit. A removal writes them after the move aside and before its check at the new path, and drops them when that check fails; the purge writes them after its re-check. Both write them before `git worktree remove`; if any of it cannot be written, it deletes nothing (`could not write its removal record, so residue deleted nothing`, result `skipped`, exit 3; a purge keeps the entry in the trash). `info` is written under another name, synced and renamed into place, the record's directories are synced, and the refs are written in one `git update-ref --stdin` transaction with `core.fsync=reference` and `core.fsyncMethod=fsync` (Git 2.36 adds `reference` to its platform default; macOS's default method only writes out), so a crash leaves all of it or none.
- Decision (#31), commits only the worktree's own reflog held are kept. `git worktree remove` deletes the worktree's Git directory and its HEAD reflog with it. A commit made on a detached HEAD and then checked out away from, or the commit before an amend or a rebase, could have that reflog as its only holder, so `git gc` deleted it after the removal although every check passed. Now the record pins those commits: one ref each, `refs/residue/reflog/ENTRY/N`, at the fewest commits that reach all of them (`git merge-base --independent` over every commit the reflog names, as an old or a new value, that no ref outside `refs/residue/` and no worktree's HEAD reaches). Another reflog naming such a commit does not count as a holder: a branch's reflog goes with `git branch -D`, and reflogs expire. A reftable repository (Git 2.45 and later) has no `logs/HEAD` file to read or copy; there residue asks Git for the commits that reflog names (`git rev-list --walk-reflogs HEAD`, each entry's new value) and pins those, and since restore cannot write that reflog back, the record stays until `--keep-removed`. The worktree's private refs (`refs/worktree/`, `refs/bisect/`, `refs/rewritten/`) and an operation in progress already keep it from removal, so the reflog is all its Git directory adds. Removal does not wait on this; it pins and goes on. The invariant, in AGENTS.md: while a record lives, nothing residue removes, restores or forgets makes such a commit unreachable.
- What `--keep-removed` can lose: once a record is forgotten, a commit only its refs held is left to `git gc`. That is the commits of a branch deleted after the removal, for example after a squash merge, and of work only the worktree's reflog held. For those, `--keep-removed` (30 days) is the only grace period. The README says so. The purge does the same.

## 0.0.5 (2026-11-07)

Deletes what you saw, or nothing, and makes a scheduled sweep reversible. Until 0.0.4, `remove` re-ran the checks right before acting, but it compared the verdict, HEAD, branch, lock and the set of ignored entries, not what they held. Measured with `scripts/race-check.sh` against the 0.0.4 release binary: a file added inside `node_modules/` while the prompt waited was deleted with the worktree (exit 0). And a scheduled sweep that took a paused agent's worktree took it for good.

- Decision, the plan is a record: for each worktree it now keeps HEAD, the branch, the lock, the staged, modified and untracked files, the file count, size and newest modification time of every ignored entry, and the modification times of the worktree's `index` and `logs/HEAD`. Right before acting, residue compares a fresh record with it and skips on any difference, with a reason that names the difference: `node_modules/ changed since you confirmed (1,204 -> 1,388 files)`, `HEAD changed since you confirmed (a82c15ee7687 -> 55c48105f23a)`, `changed since you confirmed: 1 untracked`. Under `--yes` the reason says `since the plan`. `logs/HEAD` is fine here although `--idle` must not use it: a `git gc` between plan and removal only makes residue skip.
- Decision, move aside before deleting: after the re-check, `git worktree move` renames the worktree to a hidden sibling, `.NAME.residue-removing-PID`, and residue locks it with the reason `residue: removing`. `git worktree move` is one rename by Git that updates only this worktree's record, and it refuses another filesystem instead of copying; residue skips a worktree that is a mount point. Not `mv` plus `git worktree repair`: `repair` rewrites the records of every worktree of the repository. At the new path residue checks again: Git lists it there with the planned HEAD, branch and residue's lock, a new process snapshot sees nobody inside it, and the record still matches. Then it unlocks it and `git worktree remove`, without `--force`, deletes it. On any difference or failure it moves the worktree back and unlocks it (`...; it is back in place`). This narrows the window between the last check and the deletion; it does not close it. From that check until Git finishes, a process that opens the hidden directory by its new name, or one the probe cannot see, can still write into it, and the write is deleted with it. The README says so.
- A run killed partway leaves the worktree under its hidden name, still registered. `scan` lists it under `interrupted removals` with the one command that puts it back (`git -C MAIN worktree unlock HIDDEN && git -C MAIN worktree move HIDDEN ORIGINAL`, or `git worktree remove HIDDEN` when the directory is gone), and says when the PID that moved it still runs. Neither a sweep nor `remove PATH` touches such a worktree. Scan JSON: each repository gains `interrupted`, and `summary` gains `interrupted_removals`.
- `remove --trash` moves each worktree into a trash instead of deleting it, and `--idle` turns it on, so a scheduled sweep is reversible; `--no-trash` deletes at once. Decision, where: `residue-trash/` in the repository's Git common directory (`.git/residue-trash/NAME-STAMP/`). A move there is one rename on the repository's filesystem, where linked worktrees usually live; every worktree of the repository finds it; `git status` never shows it; and it goes away with the repository. A worktree on another filesystem is refused, never copied. Each entry holds the worktree and a record, `info`, with its original path, branch, HEAD, time and size. The worktree stays registered and locked (`residue: in trash`), so restore and purge are Git commands; its branch stays checked out there until then.
- `residue restore` lists the trash of the repositories at or under the current directory; `residue restore ENTRY` (the entry name, the worktree's name or branch, or a path) moves it back with `git worktree move` and drops the entry. JSON schema `residue.restore/v1`.
- Every `remove` run purges the trash entries older than `--keep-trash DURATION` (default `7d`) in the repositories it covers, as part of the plan you confirm: each entry is checked again, without `--idle` (the trash's clock is `--keep-trash`), and deleted with `git worktree remove` without `--force`. The purge is what frees the disk, and the README says so. Remove JSON gains `trash` (`enabled`, `keep`, `keep_seconds`), `purged`, and `trash_entry` on each result; the result `trashed` is new. Scan JSON gains each repository's `trash` and `summary.trash_entries`. A sweep fails (exit 3) when an expired entry it meant to purge was skipped or failed, or a trash record could not be read; an entry kept because a check failed does not fail it.
- README: "The trash", and "Run it on a schedule" with `--keep-trash 7d` in the command, the launchd plist and the systemd service.
- JSON: each worktree's `rule_sources` is now its full effective list: `--regenerable` (`command_line`), the residue config file (`residue_config`), then its repository's Git config rules in the order Git reads them. Rules add up, so a duplicate applies once and its first entry is the source that wins. The top-level `rule_sources` stays the run-wide subset, now in the same order (`command_line` first). Before, a worktree listed only its Git config rules, so an agent judging one worktree had to merge two lists, and with Git config rules only, the top-level `[]` read as "no rules". The schemas stay at v1.
- `scripts/race-check.sh` drives the release binary's prompt under a pseudo-terminal, changes the worktree while the prompt waits (an untracked file, a modified tracked file, a file in an ignored regenerable directory, a new commit, with and without `--trash`), answers yes, and checks for exit 3, a `changed since you confirmed` reason, and the worktree still in place; two control cases must be removed or trashed. CI runs it on macOS and both Linux runners.
- Fix: a stale worktree in a sweep's `kept` list now says why it is stale.
- `residue watch ROOT...`: stays running and removes a worktree when its work landed (its upstream branch was deleted and it has been unchanged for `--grace`, default 1h) or when the disk is low (below `--min-free`, default 10%: worktrees unchanged for `--idle`, default 2d, largest first, until free space is 5 points above). No schedule: it wakes on changes under `refs/remotes`, `packed-refs` and `reftable` (inotify on Linux, kqueue on macOS and the BSDs), on the moment a waiting worktree passes its wait, and on a filesystem dropping below the threshold. Decision: `watch` deletes nothing itself. Every removal is a `residue remove --yes --idle --no-trash` child process, so it makes only removals `remove` would make. Decision, no trash: `--idle` turns the trash on, and `watch` turns it off, because freeing the disk is its job, a trashed worktree keeps every byte until a later run purges it, and nothing would purge the trash of a repository where `watch` removes nothing more. Each of its runs purges that repository's trash entries older than 7 days, and the log names each one. `--dry-run` logs instead, `--once` acts once. One `watch` per user (a lock in `$XDG_STATE_HOME/residue`).
- `residue service install|status|uninstall`: runs `residue watch` from login as a launchd agent on macOS or a systemd user service on Linux. Under Homebrew it starts the stable `bin/residue` link, so it survives `brew upgrade`.
- FreeBSD: an activity probe, from the base system's `procstat -f`. Before, FreeBSD had no probe, so nothing was ever a candidate. A packaged lsof is not used: on FreeBSD 14 it listed processes without resolving their working directories, so a worktree in use came back as a candidate. The procstat parser fails closed: a line it cannot read makes activity `unknown`.
- residue builds on illumos and Solaris, which have no `tm_gmtoff`. NetBSD, OpenBSD, DragonFly and illumos build but still have no probe, so nothing there is a candidate.
- CI runs `.github/smoke.sh` on macOS, Linux x86_64 and arm64, and FreeBSD 14 as root and as an ordinary user: a clean candidate, a kept `.env`, a worktree a process is using, and a removal that keeps the branch.
- Signed dnf and pacman repositories next to the apt one, at https://whiteheap.github.io/residue/rpm and https://whiteheap.github.io/residue/arch: `dnf install residue` on Fedora and RHEL, `pacman -S residue` on Arch and Omarchy, and `dnf upgrade` and `pacman -Syu` keep residue current. Every release updates all three. The `.rpm` files in the dnf repository are signed, and one key signs everything (`packaging/signing-key.asc`).

## 0.0.4 (2026-11-07)

Scheduled sweeps. A machine running agents all day leaked 44 worktrees (4.2 GB) in two days, so the plan was a daily unattended `residue remove`. The activity check cannot see a paused agent session: harnesses such as Claude Code reset the shell to the main checkout after every command, so a worktree whose agent is waiting for approval has no process inside it, and if its work is pushed it is a candidate. A person sees the plan before deleting; a scheduled run does not.

- `--idle DURATION` on `scan`, `explain` and `remove` (`30m`, `12h`, `2d`, `1w`; anything else, zero included, is a usage error). A worktree that changed within DURATION fails the new `idle` check, so it is `keep`, with a reason such as `changed 3 hours ago (--idle 2d)`. A last change residue cannot read makes the check `unknown`, which keeps it too. The check is reported right after `activity`. Without `--idle` it does not run, and every 0.0.3 verdict and check is unchanged.
- Decision, what counts as a change: the newest of (1) every entry the walk reaches in the checkout, ignored output included, (2) the files directly in the worktree's Git directory (`index`, `HEAD`, `ORIG_HEAD`, `FETCH_HEAD`, `COMMIT_EDITMSG`), and (3) the timestamp inside the newest HEAD reflog entry. The walk already reads every entry, so (1) costs nothing; it now also records which entry is newest. (2) catches `add`, `commit`, `checkout`, `reset`, `stash` and `fetch` when no file changed. (3) catches commits and checkouts by the time Git recorded. Not the mtime of `logs/HEAD`: measured with Git 2.50.1 and 2.43.0, `git gc` in the main checkout rewrites every linked worktree's `logs/HEAD` even when nothing expires, so its mtime would keep leaked worktrees in an active repository forever. Not the branch tip's commit time: a branch checked out in a worktree moves only through that worktree, so the reflog and index already record it, and a commit made elsewhere can be older than the checkout that brought it in. Not ctime (`touch`, `tar` and `rsync -a` set mtime on purpose) and not atime (backups and code search read every file). Reads leave no trace: measured on both Git versions, `git status`, `git diff` and `git log` on a settled worktree write nothing, and residue's own Git commands run with optional locks off, so a scan never resets the clock. The README tells people to lock a worktree that may sit without writes for longer than the idle time. Keeping a worktree that is still in use costs disk until the next run; removing one costs a paused agent its working directory, so the signal errs toward keep.
- `residue remove --all PATH...` treats each PATH as a scan root and removes every candidate under it, with the same plan, re-check and `git worktree remove` without `--force`. Decision: `remove --all --yes` is a usage error without `--idle`, because an unattended sweep without it is exactly the case above. `remove` without `--all` still takes only worktree paths, so a typo cannot turn into a sweep. A sweep exits 0 when every candidate was removed (or there was none) and 3 when a candidate was skipped or failed or part of a PATH could not be read; the worktrees it keeps are listed under `kept (N):` and do not fail it. The remove JSON gains `errors`.
- `explain` shows `last change` with the entry that set it (`index in its Git directory`, `src/main.rs in the worktree`, `HEAD reflog: commit: fix login`), replacing `newest change on disk`. The `changed N ago` fact in `scan` uses the same time. Every JSON document gains `idle` (threshold and seconds, or null); each worktree gains `last_change` (`unix`, `at`, `source`, `what`) and `last_change_error`. `size.newest_mtime` stays.
- README: "Run it on a schedule", with a launchd LaunchAgent and a systemd user service and timer for a daily 04:00 sweep, how to preview the next run, why `--idle` matters, and `git worktree lock` for sessions that may pause longer.
- Fix: rules from Git config named the wrong source. A rule from the global config (`~/.gitconfig` or `GIT_CONFIG_GLOBAL`) was reported as `This repository's git config residue.regenerable adds: ".env"`, so a reader looked in `.git/config` while the rule applied to every repository. residue now reads the key with `git config --show-scope --show-origin` and names each group of rules by scope and file: `global config (~/.gitconfig) adds ".env"; this repository's config (~/src/app/.git/config) adds "web/.tscache"`. An invalid value names its file too. In JSON, each worktree gains `rule_sources` (`rule`, `scope`, `origin`) for its Git config rules, and each document gains a top-level `rule_sources` for the residue config file (`residue_config`) and `--regenerable` (`command_line`). `regenerable_config` is unchanged: it is still the path of the residue config file, or null when there is none, and the schemas stay at v1.
- Fix: times named no zone. The header said `as of 00:23:02` in local time while `explain` said `2026-11-06 22:23 UTC`. Text output now uses local time with its UTC offset everywhere (`as of 00:23:02 +02:00`, `2026-11-07 00:23 +02:00`). JSON stays RFC 3339 UTC.
- Fix: run from `/`, as launchd and systemd start a job, residue printed every path relative to `/`, without its leading slash (`private/tmp/...`). Paths are now absolute there.
- README: regenerable rules apply only to ignored entries. An untracked file that is not ignored always blocks, and `--regenerable` does not change that.
- A signed apt repository for Debian and Ubuntu at https://whiteheap.github.io/residue/apt, so `sudo apt install residue` works and `apt upgrade` keeps residue current. It holds the latest release for amd64 and arm64, and every release updates it.

## 0.0.3 (2026-11-07)

Feedback from running 0.0.2 on an agent monorepo: a user set `residue.regenerable` through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>`, the environment form of `git -c`, and residue ignored it without a word.

- Decision: residue still ignores `residue.regenerable` set through the environment (`git -c` and `--config-env`, which Git passes on as `GIT_CONFIG_PARAMETERS`; `GIT_CONFIG_COUNT` with its pairs; the legacy `GIT_CONFIG`). Every subprocess and CI step inherits the environment, so it must not widen what residue deletes. `--regenerable` is the explicit rule for one run, and Git config files are the deliberate rule for a repository.
- It no longer ignores them silently. When the environment sets the key, residue prints a note on stderr naming the values, and points at `--regenerable` and `git config --add residue.regenerable`. Every JSON document gains `ignored_environment_rules`: the ignored values, an empty list when there are none, or null when Git could not read that environment (for example `GIT_CONFIG_COUNT=1` with no `GIT_CONFIG_KEY_0`). Git parses the variables itself, so quoting and key case follow Git. The schemas stay at v1. residue runs no extra Git process when none of the variables is set.
- Fix: 0.0.2 did not remove the legacy `GIT_CONFIG` variable. It makes `git config` read one file in place of every config file, so an inherited `GIT_CONFIG` replaced the repository's own rules, and a file it named with `residue.regenerable = .env` made a worktree holding `.env` a `candidate`. residue now removes `GIT_CONFIG` from its Git commands and reports the values in that file as ignored. It has no effect on other Git commands.
- `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM` are unchanged and documented: they choose which config files Git reads, and residue reads the same files as your Git. A user who relocates the global config keeps its `residue.regenerable` rules, as in 0.0.2. `GIT_CONFIG_NOSYSTEM` skips the system file.
- `--help` and the README say which sources count. AGENTS.md: after each release, upgrade this machine's Homebrew install.
- Linux packages on every release, for x86_64 and arm64: `.deb` for Debian and Ubuntu, `.rpm` for Fedora and RHEL, and a pacman package for Arch and Omarchy. Each is attested and listed in `SHA256SUMS`. v0.0.2 has them too.
- `packaging/aur/PKGBUILD` for the `residue-bin` AUR package.

## 0.0.2 (2026-11-06)

Feedback from running 0.0.1 on a busy agent monorepo: every worktree there held `.local-dev/` lock files, `.cargo/config.toml` and `web/.tscache/`, so nothing was a candidate unless each user added those names to a config file that then applied to every repository.

- Rules per repository from Git config: `git config --add residue.regenerable RULE`. residue reads them with `git config --get-all` in each worktree. An invalid value makes the `ignored` check `unknown` and names the value. It does not stop the scan. `explain` lists the values. residue never reads rules from a file committed to the repository, because a cloned repository must not be able to declare your files disposable.
- Path rules: a rule with a slash is a path from the worktree root (`web/.tscache`, `.local-dev/*.lock`). `*` matches within one segment. A path rule matches that entry and everything below it. Path rules work in the config file, `--regenerable` and Git config. Name rules are unchanged.
- Git reports a fully ignored directory once, as `dir/`. When a path rule reaches inside one, residue judges each file in it during the walk it already makes. The directory is regenerable only if a rule matches every file in it. `explain` names the first file that no rule matches. Above 100,000 entries, the directory is kept.
- Ignored entries show their file count and apparent size in the `scan` line, in `explain` (up to 8 entries), and on the `deletes ignored:` line of the `remove` plan, for example `ignored: .local-dev/ (2 files, 0 B), .vercel/ (2 files, 1.2 KB) (+5 more; 7 entries hold 31 files, 3.1 MB)`. Each hard-linked file counts once. JSON `ignored[]` entries gain `files` and `bytes` (null when not measured). The schemas stay at v1.
- The same walk sizes the ignored entries, judges collapsed directories and runs the safety checks. `git status` now runs before the walk. The order of the checks in the report is unchanged.
- Snapshot time: the text output of `scan`, `explain` and `remove` starts with `as of HH:MM:SS` in local time. Every JSON document has `generated_at` in RFC 3339 UTC. `explain` text now starts with the same header line as `scan`.
- `remove` still inspects each worktree twice, once for the plan and once right before deletion. Measured on macOS 26.3.1 (Apple silicon) with a 1.0 GB worktree of 46,572 entries (a pnpm `node_modules` and a Cargo `target`), over three rounds: `residue explain` took 0.65 to 0.83 s, `git worktree remove` of an identical copy took 2.69 to 3.04 s, and `residue remove --yes` took 3.68 to 4.34 s. The plan inspection is 13 to 22% of `remove --yes` (about 17% on average), under the 20% bar for removing it under `--yes`, so `remove` is unchanged.
- README: the `results[].result` values, a scan as a snapshot, `.vercel/` as a common non-regenerable entry, rules and their sources, the cost of the walk, and the platforms that ran 0.0.2.

## 0.0.1 (2026-11-06)

First release.

- `residue scan [PATH...]` lists the linked worktrees of each repository at or under PATH, with size, a verdict (`candidate`, `keep`, `unknown`, `stale`) and the reason for it.
- `residue explain PATH` shows every check for one worktree, and facts that never block: local-only commits, a gone upstream, the newest change on disk, and size.
- `residue remove PATH...` prints a plan, asks for confirmation (or accepts `--yes`), re-checks against a fresh process snapshot, then runs `git worktree remove` without `--force`. Branches and commits are kept.
- Activity probe with three states (`in_use`, `not_observed`, `unknown`): `lsof` on macOS, `/proc` on Linux.
- Ignored files block removal unless every one matches the regenerable list. Extend the list with `~/.config/residue/regenerable` or `--regenerable`.
- `--json` output for every command: `residue.scan/v1`, `residue.explain/v1`, `residue.remove/v1`.
