# How removal works

The README has the short version: [Remove a worktree](../README.md#remove-a-worktree), [The trash](../README.md#the-trash) and [Restore a removed worktree](../README.md#restore-a-removed-worktree). This page has every step and every limit.

## The plan, and the check before each removal

Before it deletes anything, residue prints the plan and asks you to type `yes`. The plan records what it showed you for each worktree: HEAD, the branch, the lock, the staged, modified and untracked files, the file count, size and newest modification time of every ignored entry, and the modification times of the worktree's index and HEAD reflog. Right before each removal, residue takes a new process snapshot, runs every check again, and compares. Any difference skips the worktree, and the reason names it:

```text
skipped .worktrees/big: node_modules/ changed since you confirmed (1,204 -> 1,388 files)
```

residue deletes what you saw, or nothing. With `--yes` there is no prompt, so the reason says `changed since the plan`.

A program that shows the plan in one run and removes in a second once you confirm passes the first run's `plan` to the second as `--expect`. Before the second run moves anything, it makes its own plan and compares. When a worktree at a PATH moved to another branch or HEAD, another worktree took its path, or it would purge or forget a trash entry or removal record the plan did not show, it removes nothing and exits 4, and the program shows the new plan ([reference](reference.md#for-coding-agents)). Without `--expect`, the second run acts on what it finds at each PATH, when every check passes.

## The move aside, and the window that remains

Then residue moves the worktree aside with `git worktree move`, to a hidden sibling named `.NAME.residue-removing-PID`, and locks it. The move is one rename on the same filesystem; a worktree that is a mount point is skipped, never copied. After the move, nothing can reach the worktree by its old path, so residue checks once more at the new path: a new process snapshot must see nobody inside it, the record must still match, no merge, rebase, bisect or other Git operation may have started in it, it must have no worktree-private refs, and the worktree must hold no `.git` entry but its own, no mount point and nothing residue cannot read. Only then does `git worktree remove` delete it. If anything differs, residue moves the worktree back, unlocks it, and the reason ends with `it is back in place`.

The move narrows the window between the last check and the deletion; it does not close it. A program that opens the old path after the move finds nothing there, and a process that was already inside shows up in the second snapshot. What remains: from that last check until Git finishes deleting, a process that opens the hidden directory by its new name, or one the probe cannot see (another user's, or one in a container or virtual machine), can still write into it, and that write is deleted with the worktree. Git checks again for modified and untracked files before it starts deleting, but not for ignored ones.

## An interrupted removal

If residue is killed between the move and the end of the deletion, the worktree stays under its hidden name and Git still lists it. The next `residue scan` lists it under `interrupted removals`, with the one command that puts it back:

```text
interrupted removals (moved aside, then stopped; part may already be deleted):
  .worktrees/.fix-login.residue-removing-4242  was .worktrees/fix-login
    put it back: test ! -e /Users/me/src/app/.worktrees/fix-login && test ! -L /Users/me/src/app/.worktrees/fix-login && git -C /Users/me/src/app worktree unlock /Users/me/src/app/.worktrees/.fix-login.residue-removing-4242 && git -C /Users/me/src/app worktree move /Users/me/src/app/.worktrees/.fix-login.residue-removing-4242 /Users/me/src/app/.worktrees/fix-login
```

The move back starts with a `test` that nothing is at the original path, since Git would move the worktree into a directory there. While something is there, `scan` says what it is and prints no move back. If its directory is already gone, the line first names `git worktree repair NEWPATH`, for a worktree you moved, and mounting its disk. When a removal record names it, the record keeps its HEAD and reflog, so the line then names the `git worktree remove` that clears Git's record. Without one, it names no command that deletes. It says that `git gc` drops Git's record, with the HEAD and reflog, 3 months by default after the worktree's index last changed, or at the next `git gc` or `git worktree prune` when it has no index, never while it is locked, and says so when Git keeps it because the `.git` its record names is still there. It names the `git reflog show` that lists the commits that may go with it; `scan --json` gives no `recovery`. If the process that moved it still runs, the line says so: it may still be removing it. While that run, or the `git worktree remove` it started, holds the removal record, `scan` prints no command and `residue restore` refuses: a move then would let Git delete the worktree where it lands. Run either again once it ends. That Git goes on after residue is killed alone, by `kill PID`, a Force Quit or `watch`'s deadline. residue never removes a worktree under a hidden name, by sweep or by PATH, so nothing touches it until you recover it. A run that stopped after it wrote the removal record adds a second line, `or: residue restore RECORD`, which moves the worktree back the same way.

A run killed during the delete can leave a worktree that Git can no longer use: its `.git` file or its HEAD is gone. Git refuses to move that worktree, so `scan` prints no move. It prints the one line that works, the restore of its record, which says what to clear and then recreates the worktree:

```text
  .worktrees/.fix-login.residue-removing-4242  was .worktrees/fix-login
    Git can no longer use it (its .git file is gone); restore says what to clear, then recreates it: residue restore /Users/me/src/app/.git/residue-removed/fix-login-20261107T040000Z
```

## Without a terminal

If stdin is not a terminal, residue does not delete anything unless you pass `--yes`. Pass `--yes` only from the session that owns the worktree and knows its task is finished, such as an agent's last step or a launcher tearing down a task, or from a scheduled `remove --all --idle` as [Run it on a schedule](automation.md#run-it-on-a-schedule) describes. Every check still runs. Without `--idle`, a session that is paused looks exactly like a finished one, so `remove --all --yes` refuses to run without it.

## The trash

Each repository has its own trash, `residue-trash/` in its Git common directory: `.git/residue-trash/` in the main checkout. Each entry is a directory named after the worktree and the time it was trashed, `fix-login-20261107T040000Z/`, that holds the worktree under its own name and a record, `info`, with its original path, branch, HEAD, the time it was trashed, the `--keep-trash` it was trashed with, and its size. The trash lives there because:

- a move into it is one rename on the repository's filesystem, the usual place for linked worktrees, so trashing takes no time and no extra space;
- it belongs to the repository: every worktree of the repository finds it, `git status` never shows it, and deleting the repository deletes its trash;
- the worktree stays registered with Git, and its record moves with it, so `residue restore` and the purge are plain Git commands.

A trashed worktree is locked with the reason `residue: in trash`, and `git worktree list` still shows it. Its branch stays checked out there, so `git switch` to that branch in another worktree refuses until you restore the worktree or the purge removes it. residue refuses to trash a worktree that is on another filesystem than its repository, because the move would be a copy; remove it with `--no-trash`, or keep it.

`residue restore NAME` takes the entry name, the worktree's directory name or branch when only one entry matches, or the path of an entry. It unlocks the worktree and moves it back with `git worktree move`, which updates Git's record, then drops the entry. It refuses when something exists at the original path again, and while a remove run purges that entry: moved back then, the worktree would be deleted where it lands. After a purge of the entry that stopped partway, the restore says part of the worktree may be gone, puts back its HEAD reflog and `config.worktree` from the purge's removal record, and drops that record once the worktree holds what it keeps. A restore counts as a change, so a sweep under `--idle` does not trash the worktree again right away.

The trash does not free disk space: a trashed worktree takes all the space it took before. The purge frees it. Every `remove` run purges the trash entries in the repositories it covers that are older than both its own `--keep-trash DURATION` (default `7d`) and the one each was trashed with, and lists them in its plan before you confirm: a run with `--keep-trash 1d` cannot purge an entry trashed with `30d`, and a run with `30d` keeps one trashed with `7d` for thirty days. An entry an earlier release made has only the run's, and one whose `keep` line this release cannot read is never purged, with a warning; `residue restore` still puts it back. The purge writes the entry's removal record, then runs every check on it again, except `--idle`, since `--keep-trash` is the trash's only clock, and deletes it with `git worktree remove`, without `--force`. An entry that someone changed in the trash stays, and the run says why. Its record is undone while the worktree still holds all it keeps; when the change took some of that, such as a commit `git reset` moved HEAD off, the record stays and the run names it in `removal_record`. A purge that finds the record of an earlier purge of the same entry, one that stopped before it deleted anything, forgets it first when the worktree still holds all it keeps, so one worktree has one record; otherwise it keeps the entry until you restore it, with a warning and that record in `removal_record`, and `residue restore` puts the worktree back. A record named for the worktree that residue cannot read may be such a purge's, so it keeps the entry the same way, with a warning naming it, and never forgets that record; while another run holds such a record, or something may still be deleting the worktree, the purge is skipped until that ends. An entry whose worktree Git lists somewhere else, as after a move into the trash that stopped partway or a repository moved since, is kept with a warning that names the `git worktree repair` that reconnects it. On a bare repository, an entry on the branch its HEAD names stays, as that branch's worktree would. A preview, or a run you do not confirm, purges nothing. An entry that holds only its record, left by a run that stopped before it moved the worktree in, is cleared by the first remove run an hour or more after it was made; a younger one may be another run's, still moving its worktree in.

residue puts nothing in an entry but the worktree and its record, and removes nothing else from it. When an entry holds anything more, the purge still deletes the worktree, keeps the record beside what is left, and says so in a warning. Each later run keeps the entry, with a warning that names what it holds, and does not fail for it; once that is moved or deleted, the next run an hour or more after the entry was made clears it. An entry with no record that holds anything, which an earlier release could leave, is kept the same way.

A program that shows the plan in one run and removes in a second, once you confirm, passes the plan's `generated_at` to the second as `--as-of`. That run then purges and forgets only what had expired when the plan was made, never an entry that expired while you read it ([reference](reference.md#for-coding-agents)).

## Removal records

A record is a directory in `residue-removed/` in the repository's Git common directory, `fix-login-20261107T040000Z/`, with an `info` file: the original path, the branch, HEAD, the upstream, why it was removed and by which command (`remove`, a `remove --all` sweep, or `watch`), when, how long it is kept (`--keep-removed`), its size, and the ignored entries the deletion took. Beside it are copies of the worktree's HEAD reflog (`HEAD.reflog`) and its `config.worktree`, when it has them. A ref, `refs/residue/removed/fix-login-20261107T040000Z`, keeps the HEAD commit, so a deleted branch, an expired reflog or `git gc` cannot lose it. The commits the worktree's own HEAD reflog names that no branch, tag, remote-tracking ref or other worktree's HEAD reaches, such as work committed on a detached HEAD that was then checked out away from, or the commit before an amend, get refs under `refs/residue/reflog/fix-login-20261107T040000Z/`, at the fewest commits that reach them all: `git worktree remove` deletes that reflog, and without the refs `git gc` would delete them. A branch's own reflog naming such a commit does not count, because `git branch -D` deletes it with the branch. A reftable repository has no `logs/HEAD` file to copy, and Git reads none that is there, so residue copies none and asks Git for the commits that reflog names, and for the ones the worktree's reflogs name that the main worktree's do not, and pins them all the same. One commit can still go unpinned there: one that only a later entry names as where HEAD came from, after the entry that moved HEAD to it expired or `git reflog delete` took it, while another reflog, such as a branch's, names it too. No Git command prints it, and that other reflog keeps it only until `git branch -D` or `git stash drop` deletes that reflog, or it expires. Restore cannot write the reflog back, and says so; a record that pins commits stays until `--keep-removed`. Restore goes by how the repository keeps its refs when it runs, so after `git refs migrate --ref-format=reftable` the same is true of a record written before the migration, which also stays for its copy of the reflog. residue writes the record and syncs it to disk after it moves the worktree aside and before its last check (the purge, before its re-check), and writes the refs in one `git update-ref` transaction, all or none. The run holds the record until its `git worktree remove` exits, and that Git holds it too, also after residue is killed; `residue restore` takes a record only when nobody holds it, and one that residue 0.0.10 or earlier wrote, which takes no hold, while Git still lists the worktree under its hidden name, only once the run it names and any `git worktree remove` of the worktree have exited. If the record cannot be written, or the last check fails, residue moves the worktree back and deletes nothing. If `git worktree remove` then fails, residue drops the record only while nothing of the worktree is gone: Git still lists it and can still use it, its files are as the plan measured them, its index is there, and its HEAD, HEAD reflog and `config.worktree` are as recorded. When residue could not move it back from its hidden name, the record stays too, and `residue restore RECORD` moves it back. Git deletes the files first, so one stopped partway, by residue's time limit or a kill, can leave everything else intact. An edit made in the hidden directory while Git ran counts the same way, and the restore brings it back with the edit. Otherwise Git deleted part of it, and the reason says so and ends with the restore command: `Git still lists it at PATH, but part of its HEAD reflog is gone; its removal record keeps its HEAD and reflog: residue restore RECORD`. The worktree stays under its hidden name; residue does not move a worktree Git deleted part of.

Each record keeps the `--keep-removed DURATION` (default `30d`) of the removal that wrote it, and no run forgets it sooner. Every `remove` run forgets the records in the repositories it covers that are older than both that and its own `--keep-removed`, after the same confirmation: a run with `--keep-removed 1d` cannot forget a record written with `12w`, and a run with `12w` keeps one written with `30d` for twelve weeks. It deletes the record and its refs in one transaction, only while each ref still names the commit the record names, and never a ref residue did not write. A record residue cannot read or forget is a warning on stderr and in the JSON `warnings`, never in `errors`, and never changes the exit status. A directory with no `info` and no ref, left by a run stopped while it wrote one, is cleared once it is an hour old. A record is small: the info file and the copied reflog, usually a few kilobytes.

What `--keep-removed` can lose: forgetting a record deletes its refs, so a commit one of them was the last holder of becomes unreachable, and the next `git gc` deletes it. Usually that is nothing, because the branch still has the commits. It is not nothing for a branch deleted after the removal, such as one deleted after a squash merge, or for work only the worktree's reflog held: there the record is the last holder, and the `--keep-removed` it was written with is the only grace period. Restore what you want before then, or put it on a branch. Tools that read every ref, such as `git log --all` and `git push --mirror`, see `refs/residue/removed/` and `refs/residue/reflog/`.

A removal and a restore wait for each other on one machine only: each run holds the trash entry or removal record it acts on with flock(2), and so does the Git it starts, and a process on another machine that shares the disk does not see that hold. On a filesystem with no flock(2), such as some network mounts, residue removes and restores nothing there and says why; for a trash entry or removal record an earlier release made there, `residue restore` names the Git commands that move the worktree back, or recreate it, by hand. While Git still lists the worktree of a record that another user's release without a hold wrote, run residue as that user to restore it, since residue cannot see another user's processes. residue tells that user by the owner of the record's `info`, which a mount that reports one owner for every file hides.

## How restore brings a worktree back

`residue restore` with no name lists the trash entries and removal records of the repositories at or under the current directory, and a name looks in the same ones. Run from your home folder, or a folder above it, they look only in the usual code folders in it, the ones `watch` uses, and say which: a search of the whole home folder would read Documents, Desktop and Downloads, and on macOS ask you for permission. When the entry is somewhere else, run `residue restore` inside its repository, or pass the record's path, as the line that reported the removal prints it.

It refuses when something exists at the path; `--to PATH` restores somewhere else. The tracked files come back as they were committed. The ignored files the deletion took, such as `node_modules/`, do not: restore lists them, and the project's install or build makes them again. The new worktree gets the saved HEAD reflog back, with the commits only it held; in a reftable repository it cannot, as above. An interrupted removal, whose record names a worktree still under its hidden name, is moved back instead, and gets the saved HEAD reflog and `config.worktree` back if Git deleted them. If Git can no longer use it, because the failed removal deleted part of its Git directory, restore cannot move it back and says how to clear it: delete the hidden directory, run `git -C MAIN worktree remove` on its path, and run the same restore again, which then recreates it. Either way, restore drops the record and its refs only once the worktree's HEAD contains the recorded HEAD and Git reads its own HEAD reflog as naming every commit the reflog refs keep. If not, for example because the branch moved while restore ran, the record stays and restore says why. Restore reads the record's copies before it changes anything. If a `remove` run forgets the record first, restore changes nothing and says so; if one forgets it while restore runs, restore still puts the saved reflog back, and when it cannot, it names each commit no ref keeps any more, which `git branch NAME COMMIT` keeps.

A restored worktree is never removed again by `watch` because its branch landed: you wanted it back after it landed. Neither is one a removal record lists as back at its path, such as after a restore that stopped before it marked the worktree, or one residue cannot tell is back. `residue remove PATH`, a sweep and `watch`'s low-disk rule still can.

## Stale worktrees

Git still lists the worktree and the directory is gone, or Git marks it prunable. Reported, not removed. If you moved it, `git -C MAIN worktree repair NEWPATH` reconnects it; if its disk is not mounted, mounting it brings it back. residue names no command that clears Git's record of it, since that drops its HEAD and reflog. `git gc` clears it on its own, 3 months by default (`gc.worktreePruneExpire`) after its index last changed, or at the next `git gc` or `git worktree prune` when it has no index, and never while it is locked; `scan` names the `git -C MAIN reflog show worktrees/ID/HEAD` that lists the commits that may go with it.

For a worktree whose directory is gone, residue reports it as `stale`. It names what brings the directory back, `git -C MAIN worktree repair NEWPATH` for one you moved or mounting its disk, and no command that clears Git's record of it: not `git worktree prune`, not `git worktree remove`. Clearing that record drops the worktree's HEAD and reflog, and `git gc` does it on its own once `gc.worktreePruneExpire` (3 months by default) has passed since the worktree's index last changed, at once when it has no index, never for a locked one, and never while the `.git` that Git's record names is there. Before then, `git -C MAIN reflog show worktrees/ID/HEAD`, which `scan` names, lists the commits that may go with it. For an orphaned checkout whose repository is gone, residue lists it and leaves it alone.

## The ledger

The numbers come from a ledger, one line per deletion, purge, move into the trash and restore: `~/Library/Application Support/residue/ledger.jsonl` on macOS, `$XDG_STATE_HOME/residue/ledger.jsonl` (by default `~/.local/state/residue/`) elsewhere. Nothing in it leaves the machine. Each size is the `reclaimable` estimate residue measured before the removal; APFS snapshots, clones and hard links can keep some of the space. A restore does not subtract from what was freed; `stats` counts restores on their own line. The ledger never decides anything: residue writes to it only after a deletion, and a ledger it cannot write is a warning that changes neither the removal nor the exit status. A removal the ledger lacks, such as one from before it existed, is added from its removal record while the record lasts. The format and the JSON are in the [reference](reference.md#stats).
