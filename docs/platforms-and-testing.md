# Platforms and testing

Back to [Tested on](../README.md#tested-on).

Each record below is one run of one release: the platform, the Git version and what happened. It is not a promise about a platform it does not name. CI runs the scripts in [What CI runs](#what-ci-runs) on every push, and `cargo test --locked` on the macOS and Linux runners.

## What CI runs

CI runs these scripts on every push: on macOS and on Ubuntu 24.04 and 26.04, x86_64 and arm64 (the recovery check there also as root, for its mount cases, and on Ubuntu 24.04 x86_64 again with statx refused), and as root and as an ordinary user in FreeBSD 14, NetBSD 10, OpenBSD 7.8 and DragonFly 6.4 virtual machines. An OmniOS (illumos) virtual machine runs the smoke test and the contract and recovery checks, as root and as an ordinary user, root's contract check in `/tmp`, a tmpfs, and the user's on ZFS; not the watch smoke test, because without inotify or kqueue a running `watch` wakes on its five-minute timer, past that test's two-minute limit, and not the race check, because illumos `script` cannot run a command and the base system has no other way to give residue a terminal. On NetBSD, OpenBSD and DragonFly nothing is a removal candidate, so each script skips every case that expects a removal or a prompt, naming the case and the reason (`scripts/partial-probe.sh`), and checks instead that the clean, idle worktree is kept as `unknown` for the probe's reason (`partial_probe`), with nothing moved aside or put in the trash. The gate is the system's name, so a residue that offered a removal there would fail it.

- `.github/smoke.sh`, in a scratch home folder: a clean candidate, a kept `.env`, a worktree a process is using, a removal that keeps the branch and ends with what it freed, a restore of it from its removal record, and both read back from `residue stats --json`.
- `scripts/race-check.sh`: five changes made while the prompt waits, each skipped; an upstream restored while it waits, kept with and without the trash; and three removals that changed nothing.
- `scripts/recovery-check.sh` (needs `jq`): what `remove` leaves when it is stopped right before `git worktree remove` (still registered under its hidden name, its bytes intact, listed by `scan` with the line that moves it back, and not removed by a later run); when the check after the move fails (back in place), also for what `git status` does not list: a repository made in a tracked folder, a volume mounted at an ignored path, a folder from the worktree's own filesystem mounted at one (also before the plan, where `mount_point` keeps the worktree), or a folder nobody can read; when the move back fails too, or something now occupies the original path (`failed`, locked under its hidden name, with where it is, the line that unlocks and moves it back, and its removal record, whose restore moves it back); and when a second remover of the same worktree runs after the first, with and without the trash (one removes it, the other fails at Git's move, one trash entry at most). The stopped run has written its removal record, so `residue restore` lists it as interrupted and moves it back with every file; the other cases check how many removal records and refs each leaves. A `git` script first on `PATH` stops or fails one Git command at a time; nothing in residue knows about it. Three cases fail `git worktree remove` after it deleted part of the worktree, its HEAD reflog or its HEAD from Git's directory for it, or the `.git` file from its checkout: the worktree stays under its hidden name and the removal record with its two refs stays, with the commit only the reflog held surviving `git gc`; restore then moves it back with every file, or, when Git can no longer use it, says to delete it and run `git worktree remove` on its path, after which restore recreates it. For those two, `scan` prints only the restore of the record, in its text and in `recovery`, and no move Git would refuse. A fourth runs that restore while the removal that left the worktree still runs: restore says that run holds the record and changes nothing. A fifth stops Git after it deleted one ignored file, with its Git directory whole: the record stays because the files differ from the plan, and restore moves the worktree back. Three cases cover a Git that may still be deleting: residue killed alone while its `git worktree remove` runs (`scan` gives no command and restore refuses until that Git exits, then restore moves the worktree back), a trash restore while a purge deletes the entry (restore refuses, the purge completes, and its record brings the worktree back), and a purge killed with its Git partway through (the trash restore says part of it may be gone, puts the HEAD reflog back from the purge's record, and drops that record). Four more cover records and holds: a removal record, and a purge's record, without a hold line that names a process still running, as 0.0.10 and earlier write them (`scan` gives no command, and both kinds of restore refuse until that process exits); a record residue can read but not write, which `scan` still checks, and one it cannot read, for which `scan` gives no command and says why; and a purge stopped after Git deleted the worktree's files (the trash restore names the record's restore, which clears what Git kept in the trash and recreates the worktree). Two more check that `scan` names no command that deletes and gives the repair first, which brings back a worktree moved by hand, and that for a hidden worktree whose directory is gone and that no record names, `recovery` is empty while the text gives that repair first. And a `watch` removal's log line names its `residue restore` command, its record says `by watch`, the restore brings the worktree back, a fetching `watch` keeps it past `--grace` after its branch landed, and disk pressure still removes it. Its log says what a removal freed, and `residue stats` counts it under `watch`; the script runs in a scratch home folder, so it never writes the caller's ledger. Then `watch`'s fetch in repositories whose remote has refspecs into `refs/tags/` and `refs/notes/` and `pruneTags` set, or `fetch.pruneTags` alone: a dry run and a real pass each prune a branch deleted on the remote, keep every local tag and note, those the remote lost included, and fetch no tag, and a remote with no refspec into `refs/remotes/` (a `.git/remotes` file) is not fetched, logged once, its refs as they were. A second remote whose extra refspec stores into `refs/remotes/origin/` is fetched without it, logged once, and `origin/mine` stays, so its worktree, past `--grace`, is not taken as landed; with remotes `origin` and `origin/fork` neither is fetched and `origin/fork/b` stays; a symbolic ref under `refs/remotes/origin/` that names a local branch stays, the branch does not move, and that remote is still fetched and pruned. That case runs on NetBSD, OpenBSD and DragonFly too. Last, a running `watch` started by an absolute link exits 1 between passes once the link names another file, as `brew upgrade` leaves it, and its log says why; its first line ends with its version. That case runs everywhere the script does. And a running `watch` whose pass record cannot be written (a folder in its place) logs that once and goes on; once it can, the next pass writes the record with that pass's counts, `residue stats --json` has it as `watch_pass`, and `service status` prints its `last pass:` and `next pass:` lines; the log has one `pass:` line for the two passes that found the same, and a second once a worktree gets an untracked file. That case runs everywhere the script does. `.github/service-smoke.sh` installs, checks and uninstalls the launchd agent on macOS and the systemd user service on Linux: with a ROOT, again without one (the ROOT is kept), and after an uninstall without one (the usual code folders, marked as such in `service status`; a GitHub runner has `~/work`). It replaces this user's service, so it runs only on CI runners.

## Git behavior the checks rely on

Observed 2026-11-08: Git 2.50.0 to 2.56.0 swap the two reflog expiry defaults that Git documents (`gc.reflogExpire`, 90 days; `gc.reflogExpireUnreachable`, 30 days, for an entry not reachable from the current tip). `git gc` and `git reflog expire` on those versions drop every entry older than 30 days, reachable or not. Git commit 8565827570 (2025-04-08) made the swap, and 60cf500551 (2026-09-24) fixes it on `master`, after 2.56.0. In a reftable repository the commit HEAD left from can then be only the oldest entry's old value, which residue reads as `HEAD@{N}`. The contract case `record-reflog-reftable-expired` dates its entries 60 and 10 days back, so its gap is the same on both defaults. To re-check a Git:

```sh
cd "$(mktemp -d)" && git init -q && GIT_COMMITTER_DATE="$(($(date +%s) - 60 * 86400)) +0000" git -c user.name=x -c user.email=x@example.invalid commit -q --allow-empty -m old && git reflog expire --dry-run --verbose HEAD
```

It prints `keep commit (initial): old` on the documented defaults (Git 2.47.3) and `prune commit (initial): old` on the swapped ones (Git 2.50.1). A release's source says the same: `gh api "repos/git/git/contents/reflog.h?ref=v2.56.0" -H 'Accept: application/vnd.github.raw' | grep -A3 'define REFLOG_EXPIRE_OPTIONS_INIT'` shows `default_expire_total` at 30 days and `default_expire_unreachable` at 90.

Observed 2026-11-08 on Apple Git 2.50.1: Git's directory walk skips an entry whose name is `.git` by `fspathcmp`, which is `strcasecmp` when `core.ignorecase` is set (`git init` sets it on a case-insensitive file system, as macOS has by default), so it skips `.GIT` and every other case of the name at every level, the root included, and `git status` lists nothing inside one. residue's `nested_repo` check therefore blocks on any case of `.git` except the root's own `.git` link (#102); the contract cases `ignored-dotgit-upper-ignorecase`, `ignored-dotgit-upper-case-sensitive`, `ignored-dotgit-plain-folder` and, on a case-sensitive file system only, `ignored-dotgit-upper-root` hold it. The source: `gh api "repos/git/git/contents/dir.c?ref=v2.50.1" -H 'Accept: application/vnd.github.raw' | grep -n 'fspathcmp(cdir->d_name, ".git")'`.

Observed 2026-11-08 on Apple Git 2.50.1: on macOS, `git init` sets `core.precomposeunicode`, and Git then precomposes (NFC) every name it reads that holds a non-ASCII byte, with `iconv` from UTF-8-MAC to UTF-8, before it prints it (`precompose_utf8_readdir`). APFS keeps a name as it was written, so a folder written decomposed (NFD) is printed in a spelling the disk does not hold. residue's walk looks a non-ASCII path up in its stored spelling and then in Git's, through the same conversion (#103); the contract cases `ignored-nfd-folder-size` and `ignored-nfd-folder-path-rule`, with their precomposed controls, hold it. Git converts one name at a time and keeps a name the conversion refuses as stored; on macOS 26.3.1 Apple's converter refused every character above U+FFFF tried, such as U+1F680 and U+20000 (observed 2026-11-09), so one path can hold a name Git composed and a name it kept. residue converts name by name too; the contract cases `ignored-mixed-names-env`, `ignored-mixed-names-env-swapped` and `ignored-mixed-names-clean` hold it on macOS and are skipped by name elsewhere. An ignored entry the walk still does not reach is `unknown`, whatever the rules say. Other systems print a name as stored: Git builds the conversion only for Darwin. The source: `gh api "repos/git/git/contents/compat/precompose_utf8.c?ref=v2.50.1" -H 'Accept: application/vnd.github.raw' | grep -n 'UTF-8-MAC\|precomposed_unicode == 1'` and `gh api "repos/git/git/contents/config.mak.uname?ref=v2.50.1" -H 'Accept: application/vnd.github.raw' | grep -n 'Darwin\|PRECOMPOSE'`.

## The activity probe on each platform

The README has the summary: [What the activity probe can and cannot see](../README.md#what-the-activity-probe-can-and-cannot-see).

- **macOS**: one `lsof` snapshot of the working directories and open files of the processes your user can inspect. residue reports how many processes that covered, for example "lsof inspected 506 of 807 running processes". A process whose working directory or files lsof could not read does not count as inspected. lsof also leaves out, with no error, every process it may not inspect: another user's, and, when residue runs in a sandbox that lets it list processes but inspect only its own, every process of yours outside it. So residue lists every process (`proc_listallpids`) before lsof runs, and once lsof is done looks up each one it did not list (`proc_pidinfo`, then the `kern.proc.pid.PID` sysctl), and each one lsof listed but printed a name in place of a file for (`FD info error`, which a sandbox that denies `process-info-pidfdinfo` leaves). lsof is asked once more for those alone (`-p`): one that launchd was starting as lsof read it is listed then. One that exited meanwhile, or runs as another user, does not count. One that runs as your user, or whose user residue cannot read, makes activity `unknown` (`probe_failed`), and the reason says how many and names one ("lsof could not read every file of ..." for the second kind): "lsof did not list 534 running processes of yours, such as zsh[25712]: a sandbox around residue may hide them". lsof runs in `/`, so it never shows up as a process using the worktree you run residue from. lsof prints a byte of a name that is not printable ASCII, and a backslash, escaped (`é` as `\xc3\xa9`), so residue writes the worktree's path the same way before it matches; a path with a byte whose printed form residue has not confirmed (0xff) is `unknown` (`unmatchable_path`). lsof prints a path of 1,024 bytes or more cut short (measured on macOS 26.3.1), so a worktree that holds a path of 1,004 bytes or more is `unknown` (`long_path`): 20 bytes less, for the `/System/Volumes/Data` the kernel can put in front of a path.
- **Linux**: `/proc/*/cwd`, `/proc/*/exe`, `/proc/*/fd` and `/proc/*/maps`, for the processes your user can read. `maps` names the files a process has mapped into memory: a native module that a process started elsewhere loaded from a worktree's `node_modules` holds no open file there, and is seen only through it. A process whose open files or mapped files residue cannot read does not count as inspected. When one process's `maps` is longer than 64 MiB, activity is `unknown` (`probe_failed`), because residue did not read the rest. The kernel names no working directory or open file of 4,096 bytes or more there, so a worktree that holds a path that long is `unknown` (`long_path`). When residue runs in a PID namespace other than the initial one, as in a container (`/proc/self/ns/pid` is not `pid:[4026531836]`, or `NSpid` in `/proc/self/status` lists more than one PID), its `/proc` shows only the processes in that namespace, so a worktree with no use found is `unknown` (`hidden_processes`): "residue runs inside a container (a PID namespace of its own), so it cannot see processes outside it". A WSL distribution is the exception: under WSL 2 each distribution has a PID namespace of its own in one virtual machine, and it holds the user's whole Linux session; what is outside is other distributions and Windows programs, which residue cannot see on any setup. residue counts it as WSL only with proof that the `/proc` it reads is the distribution's own: `/proc/sys/kernel/osrelease` names Microsoft's kernel, WSL's `/init` is a process there (PID 1, or another with systemd as PID 1), and none of `/.dockerenv`, `/run/.containerenv`, `/run/systemd/container` and `/run/host/container-manager` exists. WSL's variables and `/run/WSL` are no proof: a sandbox started in a distribution (bwrap, firejail, `unshare --pid`) keeps them, and a container on WSL's kernel, as Docker Desktop runs one, reports the same kernel; both are still containers. What `/proc/1/cmdline` shows on WSL 2 with and without systemd was not checked on a real machine. A user namespace other than the initial one (`/proc/self/ns/user` is not `user:[4026531837]`), as toolbx and distrobox run one, is `unknown` (`hidden_processes`) too: "residue runs in a user namespace of its own, so it cannot see processes outside it"; the kernel shows a process outside it only to one with `CAP_SYS_PTRACE` over it. So is a worktree under a `/proc` mounted with `hidepid` (any value but `0` or `off`), unless residue is in the mount's `gid=` group, which `hidepid=ptraceable` does not let see more, or holds `CAP_SYS_PTRACE` in the initial user namespace, as root does: it hides every process residue may not inspect, some of yours among them. A process of yours that the kernel will not show residue makes activity `unknown` (`probe_failed`), and the reason names it: `/proc/PID/status` is yours, so the process is dumpable, but its `fd` or `maps` answers Permission denied, as for one started with another of your groups (`sg`, `newgrp`, or a container's `docker run --user UID:GID`) or one outside a Landlock sandbox around residue. Such a process is read once more first, so one that changes its user as residue reads it (cron, sshd, su) does not count; it fails the probe only when it is still refused and its credentials held. The reason says which check refused: its user ids, its group, or else a sandbox or security module. One that is not dumpable, such as ssh-agent (`status` is root's), and one that holds a capability residue does not have in effect (its `CapPrm`), such as systemd's user manager on some systems, the kernel shows only to root, and they are not inspected.
- **FreeBSD**: the base system's `ps` lists every process, then the `kern.proc.filedesc.PID` sysctl, the one procstat(1) reads, gives each process's working directory, executable and open files, and `kern.proc.vmmap.PID` the files it has mapped into memory, every path byte for byte, for the processes your user can inspect. The kernel names a file from its name cache. One it cannot name comes back with its filesystem and inode: residue looks for that inode in the worktree, so such a file inside it is a use, and one residue cannot place is `unknown` (`unnamed_file`). Some processes of yours the kernel shows only to root, whatever the settings. These are a process whose credentials changed since its last exec, such as the one sshd keeps for each login, a process that turns tracing off, such as ssh-agent, and init. They are not inspected, as on Linux, and `ps` gives each process's flags to tell them apart. When the kernel refuses any other process that runs as your user, as it refuses every one with `security.bsd.unprivileged_proc_debug` set to 0, activity is `unknown` (`probe_failed`): residue cannot see that process's files. A worktree that holds a path of 1,024 bytes or more is `unknown` (`long_path`). procstat itself is not run: it prints a name through libxo, which in the C locale rewrites a character that is not ASCII. An answer residue cannot read is `unknown` (`parse_error`). A packaged lsof is not used: in testing on FreeBSD 14 it listed processes without resolving their working directories, which would have hidden a worktree in use. A process whose working directory the kernel cannot name does not count as inspected. Every release since 0.0.5 has a FreeBSD x86_64 binary, `residue-vX.Y.Z-x86_64-unknown-freebsd.tar.gz`, and every release since 0.0.6 also has an aarch64 one, `residue-vX.Y.Z-aarch64-unknown-freebsd.tar.gz`, on the [releases page](https://github.com/whiteheap/residue-cli/releases). Each is built from the tag's source, run and smoke-tested in a FreeBSD 14 virtual machine of its own architecture; the aarch64 machine is emulated on an x86_64 runner. Inside a jail (`security.jail.jailed` is 1) the kernel shows only the jail's processes, and a process outside can share the jail's files, so a worktree with no use found is `unknown` (`hidden_processes`): "residue runs inside a jail, so it cannot see processes outside it". With `security.bsd.see_jail_proc` at 0, a process that is not root sees another only in its own prison (`cr_canseejailproc` in `sys/kern/kern_prot.c`), so residue on the host, not root, cannot see your processes in the jails; when one exists, a worktree with no use found is `unknown` (`hidden_processes`) as well.
- **NetBSD, OpenBSD and DragonFly**: the base system's `ps` lists every process, then one sysctl per process asks the kernel for its working directory (`kern.proc_args.PID.cwd` on NetBSD, `kern.proc_cwd.PID` on OpenBSD, `kern.proc.cwd.PID` on DragonFly), and on NetBSD and DragonFly for its executable too. Open files are not read: a process that works elsewhere but holds a file open inside the worktree is not seen. So on these three systems residue never offers a worktree for removal on activity grounds. Activity is `in_use` when the probe finds a process inside the worktree, and `unknown` otherwise, never `not_observed`, so nothing there is a removal candidate and `remove`, `--all` and `watch` remove nothing. `scan` shows such a worktree as `unknown` with `activity unknown (partial_probe)`, its header says what the probe read ("sysctl inspected 9 of 41 running processes, working directories only, not open files"), and `explain` says why: "sysctl reads working directories only, not open files, so it cannot show that no process is using it" (NetBSD and DragonFly: "working directories and executables only"). Remove a worktree there with `git worktree remove`. `fstat` is not used: on NetBSD and OpenBSD it names an open file only by its mount point and inode ("Normally the name cannot be determined", fstat(1)), so it cannot say whether a process is inside a worktree. A process whose working directory the kernel does not name does not count as inspected, and when it names none at all, activity is `unknown`. As an ordinary user, OpenBSD names only your own processes' working directories; NetBSD and DragonFly name every process's by default.
- **illumos**: `/proc/PID/path/`, which names each process's working directory, every open file descriptor and every mapped object, the executable among them (proc(5)), for the processes your user can inspect. Not `/proc/PID/cwd`, whose readlink yields an empty string. A process whose working directory has no path there does not count as inspected. A file a process holds that has no path there is looked for by its inode: residue walks the worktree for it, and where it cannot look, activity is `unknown` (`unnamed_file`). A deleted file does not count. A worktree that holds a path of 1,024 bytes or more is `unknown` (`long_path`). illumos has no inotify or kqueue, so a running `residue watch` acts on its five-minute timer instead of on change events. In a non-global zone (`getzoneid()` is not 0) the kernel shows only the zone's processes, and a process in the global zone can share the zone's files: the zone's root is a folder of the global zone's, and a `lofs` mount (zonecfg(8)) brings in any other. So a worktree with no use found is `unknown` (`hidden_processes`): "residue runs inside a non-global zone, so it cannot see processes outside it".

The probe has three answers. `in_use` means a process was seen inside the worktree. `not_observed` means none of the inspected processes was inside it. `unknown` means the probe failed: its tool is missing, it timed out, it failed, residue could not parse its output, or a running process of yours was hidden from it: on macOS lsof did not list it, on Linux the kernel would not show its files. On Linux in a container or under a `/proc` with `hidepid`, on FreeBSD in a jail and on illumos in a non-global zone, it is `unknown` (`hidden_processes`) whenever no use is found. On NetBSD, OpenBSD, DragonFly and illumos it is also `unknown` when the probe inspected no process at all. On NetBSD, OpenBSD and DragonFly it is `unknown` whenever no use is found, because a probe that does not read open files cannot show that a worktree is unused. In JSON, each worktree's `activity` is `{"state", "processes", "reason", "detail"}`: `state` is `in_use`, `not_observed` or `unknown`; `processes` lists `{"pid", "command"}` for `in_use` and is empty otherwise; and for `unknown`, `reason` is one of `probe_missing`, `timeout`, `probe_failed`, `parse_error`, `unsupported`, `partial_probe` (the probe found no use and does not read open files), `unmatchable_path` (the probe prints paths escaped, and residue cannot be sure how it prints this one), `long_path` (the worktree holds a path as long as the probe names whole, or longer, here or where residue would delete it) `unnamed_file` (a process holds a file whose path the probe could not read, and residue could not look for it in the worktree) or `hidden_processes` (residue runs where processes of yours can be hidden from it: a container, a `/proc` with `hidepid`, a jail or a non-global zone), and `detail` says why in words. Both are null otherwise.

`not_observed` is not proof that a worktree is idle. The probe cannot see processes owned by other users, processes inside containers or virtual machines, processes on other machines that share the disk, on WSL a process in another distribution or a Windows program using the worktree through `\\wsl$`, or a session that is closed now but that you mean to resume.

A process can also open the directory a moment after the snapshot; residue moves the worktree aside and looks again before it deletes, which narrows that gap but does not close it. That is why removal asks a human, why `--yes` belongs to the session that owns the work, and why a scheduled sweep needs `--idle`.


## Mount points

`git worktree remove` deletes what is under a mount point inside the worktree, then stops at the mount point (observed 2026-11-09 with Git 2.43.0 on Linux 7.0.14). So the walk counts each entry on another mount than the worktree's folder as `mount_point`, and reads nothing below it:

- **Everywhere**: a folder on another device (`st_dev`). Everywhere but Linux, a file on another device too: FreeBSD's nullfs mounts a file over a file from 14.0. On Linux a file on overlayfs can show the device of the layer it comes from, so there only a folder counts by its device.
- **Linux**: an entry whose mount ID (statx(2), `STATX_MNT_ID`, Linux 5.8 and later) is not the worktree folder's, or that statx marks the root of a mount (`STATX_ATTR_MOUNT_ROOT`). A bind mount of a folder or a file from the same filesystem keeps its device; its mount ID tells it. Where statx gives no mount ID, the walk takes each mount point `/proc/self/mountinfo` lists inside the worktree: before Linux 5.8, under a seccomp filter that refuses statx, and under qemu-user before 11, which gives every mount ID as 0. One statx of `/` per process decides whether statx is there: any error there means it is not, and after it any error is that entry's, which makes `contents` `unknown` (a FUSE filesystem with no getattr answers `ENOSYS`).
- **illumos**: each mount point `/etc/mnttab` lists inside the worktree, and each entry with the device and inode of the source of a lofs mount on the worktree's device. A loopback mount (lofs) takes the device of the filesystem it shows and passes its source's attributes through (`lo_getattr`, `lo_mount` in illumos-gate). mnttab keeps the path a mount had when it was mounted (`vfs.c`), so after a folder above it is renamed, as `git worktree move` renames one, the table names the old path; and a mount made later on a folder that a lofs mount shows is seen through that one too (`lo_lookup` calls `traverse`), at a path the table does not list. The source's device and inode tell both. residue looks up only the sources of lofs mounts on the worktree's device, or whose device the table does not give (`dev=ffffffff`, `NODEV32`), and the mount point where the source does not lead to that device (in a zone, a source in the global zone is not there to look up), from `/` one name at a time and never through a symbolic link: a lofs mount on another device counts by its device, and a lookup of a path on another filesystem could wait on a network server or mount an automounted home. Such a mount that neither lookup leads to on the device makes `contents` `unknown`, and so does a line of the table with other than five tab-separated fields. That holds for every worktree on that device, and its detail names the mount and why, such as `cannot tell what the lofs mount at /zones/z/root/data shows: looking up /export/data: /export: Permission denied (os error 13); looking up /zones/z/root/data: /zones/z/root: Permission denied (os error 13)`: a user who cannot look up either path, as under a zone root only root may enter, keeps every worktree there until root runs residue or the mount goes. In a non-global zone, a mount the global zone makes on a folder that one of the zone's lofs mounts shows is in no table the zone can read, and residue there does not tell it.
- **macOS, FreeBSD and NetBSD**: the device alone. FreeBSD's nullfs and unionfs, NetBSD's null mounts, and macOS's devfs and nullfs give each mount a device of its own (`null_getattr`, `unionfs_getattr`, `layer_getattr`, `vfs_getnewfsid`), and a disk mounts once. FreeBSD after 15.0 also marks a mount's root in `st_bsdflags` (`SFBSD_MNTPOINT`); residue does not read it, as the device tells the same there. Read in the kernels' sources; FreeBSD's nullfs also runs in CI.
- **OpenBSD**: the device alone. It has no null mount, every mount has a device of its own, and nothing there is a candidate (`partial_probe`).
- **DragonFly**: a null mount keeps the device of the folder it shows (its nullfs has no `getattr` of its own), and residue does not tell it. Nothing there is a candidate (`partial_probe`).

Where the walk reads the mount table, it reads it again after the walk. A table it needs and cannot read, or a mount inside the worktree, or on illumos a lofs source on its device, that the second read finds and the first did not, makes `contents` `unknown`. As root, `scripts/recovery-check.sh` mounts a folder from the worktree's own filesystem inside a worktree, before the plan and after the move aside, and a file over a file where the system can, and one in a worktree it then renames with `git worktree move`: a bind mount on Linux, nullfs on FreeBSD and lofs on illumos. CI's `ubuntu-24.04` job runs it again with statx refused (`.github/nostatx.c`), so the walk reads `/proc/self/mountinfo`.
