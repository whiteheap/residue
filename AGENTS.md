# Agent guide

residue is a Rust CLI that judges and removes Git linked worktrees. The README is the user contract. This file is for agents changing the code. The Mac app, a window over this CLI, is [whiteheap/residue-ui](https://github.com/whiteheap/residue-ui), with its own rules.

## Invariants

These are the reasons people trust the tool. Do not weaken them without an explicit decision recorded in the CHANGELOG.

- Deletion only through `git worktree remove` without `--force` (`git::remove_worktree`). Never `rm`, never `--force`, never branch deletion, never killing processes. `git worktree unlock` only for a lock residue set itself (`remove::REMOVING`, `trash::LOCK`), never anyone else's. Moves only through `git worktree move` (one rename by Git, which updates only that worktree's record and refuses another filesystem); never `mv`, never a copy, never `git worktree repair`, which rewrites every worktree's record.
- A worktree is removable only when every check in `inspect::worktree` passes. An `unknown` check blocks, the same as a failed one.
- Activity has three states (`in_use`, `not_observed`, `unknown`). A probe failure is `unknown`, never `not_observed`. So is finding no use with a probe that does not read open files (`activity::Seen::limits`, set on NetBSD, OpenBSD and DragonFly): it can show a use, never its absence, so `Snapshot::evidence` answers `unknown` (`partial_probe`) and nothing there is a candidate. A new backend that reads less than working directories and open files sets `limits`; never clear it to make worktrees removable. A worktree that holds a path as long as `activity::PATH_LIMIT`, the longest the platform's probe names whole, is `unknown` (`long_path`). The plan also counts where residue will delete it (`remove::deleted_at`, `Snapshot::evidence_at`), so a candidate is never one the check after the move keeps. A walk measures the longest path (`fsinfo::Reach`): the walk that sizes the worktree, or, for an unfinished removal record, one of its own (`removed::reach`). A process running as your user that the kernel refuses to show is a probe failure, never skipped. The one exception is a process the kernel shows to root alone whatever the setting: on FreeBSD (`Listed::guarded`), one whose credentials changed since its last exec, one that turns tracing off, or init. Such a process is not inspected, as Linux's non-dumpable processes and illumos's unreadable ones are not, and the README names that gap.
- A use matches a worktree by bytes. A backend whose tool prints paths escaped sets `activity::Seen::spelling` (lsof on macOS: `activity::lsof::spell`, its escape table from lsof's source and checked against lsof's output), which writes the worktree's canonical path the same way before matching; a path it cannot write with certainty is `unknown` (`unmatchable_path`), never `not_observed`. A backend that reads the kernel's bytes sets none. Never compare an escaped name with a raw path. A file a process holds whose path the kernel cannot give (illumos `/proc/PID/path/N`, `activity::unnamed`; FreeBSD a `kern.proc.filedesc` or `kern.proc.vmmap` record with no path) is recorded by device and inode (`activity::Seen::unnamed`). A directory a walk finds it in is in use by that process: the walk that sized the worktree (`fsinfo::Reach`), or `activity::inodes_within` where none ran. Where residue cannot read the file's device and inode, the directory's, or all of the directory, it is `unknown` (`unnamed_file`), never `not_observed`. Skip such a file only where the kernel's source shows it cannot be in a worktree.
- `remove` deletes what the plan showed or nothing. The plan records an `inspect::Fingerprint` (HEAD, tracked and untracked changes, each ignored entry's file count, size and newest mtime, the `index` and `logs/HEAD` mtimes). Right before acting it re-inspects against a fresh activity snapshot and compares; any change skips the worktree, with a reason that names it. Then it moves the worktree aside (`.NAME.residue-removing-PID`, or into the trash), locks it, and checks again at the new path (Git's record, a fresh snapshot, `Fingerprint::again`) before `git worktree remove`. That last check also refuses what the walk finds there and the fingerprint does not hold: a `.git` entry (`nested_repo`), a mount point, an unreadable entry. On any doubt it moves the worktree back. Never claim this is atomic: the README documents the window that remains.
- `watch` deletes nothing itself. It only chooses which paths to pass to a `residue remove --yes --idle --no-trash` child process, so every removal it makes is one `remove` would make. Its reason travels with the paths: a work-landed removal passes `--only-if-upstream-gone`, which the child checks from fresh local refs at the plan, in the re-check before the move, and last in `verify_moved` right before the deletion, so a reason that went stale between the scan and the deletion keeps the worktree. `inspect::upstream` counts an upstream as gone only when its ref is absent; Git's `[gone]` for a ref that exists but does not resolve to a commit is an error, never gone. Work landed also needs the upstream to be a remote-tracking ref (`Upstream::remote`), in both `watch` (from `upstream_ref`) and the child. It reads `scan --json` and `remove --json`, so the JSON schemas are its contract too.
- `watch` fetches only through `git::fetch`, from `watch::Fetcher`: `git fetch --prune --no-tags --no-write-fetch-head --no-auto-maintenance --no-recurse-submodules` of the remotes that a linked worktree's branch tracks, in the main checkout, in a new session with no terminal, with prompts off (`GIT_TERMINAL_PROMPT=0`, `SSH_ASKPASS_REQUIRE=never`, `GCM_INTERACTIVE=never`), SSH `BatchMode=yes` unless the user set an SSH command, and a deadline. A fetch only refreshes the remote-tracking refs that the scan and the child read: it is never itself a reason to remove, and a failed one is logged and changes nothing. It never writes `FETCH_HEAD` or anything else in a worktree's Git directory, whose files are the idle clock. `scan`, `explain` and `remove` never fetch, so the child's three upstream reads stay local.
- `watch` exits for an upgrade only between passes, never while a `scan`, `remove` or fetch it started runs: `watch::Binary` is checked at the top of its loop, of `wait`, and of `wait_for_git` (a running watch on a Git too old, before its first pass), and nowhere else (#149). It exits 1, so launchd's `KeepAlive` and systemd's `Restart=on-failure` start the new release.
- Without a ROOT, `watch` and `service install` use `watch::DEFAULT_ROOTS` that exist in the home folder: never the home folder itself or a folder above it, never `Documents`, `Desktop` or `Downloads` (macOS asks a background process for permission there). `service install` writes the resolved roots into the service, and `service status` shows them. Run again without a ROOT, it keeps the roots a user named; only a service carrying `service::DEFAULT_MARK` looks for the default ones again.
- `service install` and `uninstall` run one at a time: an exclusive flock(2) on the folder of the service file (`service::lock`), taken right before the write and held until they return. `service install --expect` compares the service with the fingerprint `service status` printed under that lock, right before the write, and on a mismatch writes nothing and exits 4 (`service::CHANGED`). The fingerprint (`service::fingerprint`) covers the file's bytes, the resolved path of the binary it starts, launchd's loaded state and the release. The Mac app passes it on every save: changing what it covers changes when a save is refused, so it changes only with the app.
- Every deletion is restorable: `remove`, `remove --no-trash`, a sweep, `watch`'s child and the trash purge each write a removal record before `git worktree remove` (`removed::create`): `GIT_COMMON_DIR/residue-removed/ENTRY/info` (written as `info.new`, synced, renamed; it names the command, `by`), copies of the worktree's `logs/HEAD` (`HEAD.reflog`), only while the repository keeps its refs in files (`git::is_reftable`), and `config.worktree` when it has them, then the entry and its parents synced, then the refs. A removal writes it after the move aside and before `verify_moved`, and a failed `verify_moved` undoes it; the purge writes it after its re-check. If any of it cannot be written, nothing is deleted: the worktree goes back in place (`skipped`) or, in the trash, stays. A deletion that then fails undoes the record only while nothing of the worktree is gone (`remove::standing`): Git still lists it, its checkout and `.git` file are there, Git can still use it, its HEAD contains the recorded HEAD, its `logs/HEAD` still begins with the copy and its `config.worktree` is the copy (`removed::Written::lacks`), and, once Git ran, its files are as the plan measured them (`remove::Files`: Git deletes the files first, and one stopped partway leaves the rest intact). Otherwise the record stays, so `residue restore` still has the commits, and a worktree Git deleted part of stays where it is, never moved back.
- A run that may delete or move a worktree holds the entry that names it: an exclusive flock(2) on its `info` (`hold::take`, never blocking). A removal holds its record from `info.new` on (`hold::write_new`), and `remove --trash` its trash entry the same way (`trash::create`); a purge holds the trash entry before its re-check, then its record; and `git worktree remove` inherits both (`hold::pass_to`), so they stay held while Git deletes, also after residue is killed alone. A restore takes the hold before it reads Git's list of worktrees or moves anything, a trash restore also on the records of purges of that entry that stopped partway (`removed::stopped_purges`), and refuses, changing nothing, while another process holds one. residue unlocks only a lock it read under the hold. `scan` reads a held record as `removal_running` and gives no recovery line for it. A record says its writer holds it (`hold flock`, `Record::hold`). One without that line comes from 0.0.10 or earlier, which hold nothing, so wherever a free hold stands for "no run is active" (`removed::restore`, `removed::stopped_purges`, `Item::activity`), and only while Git still lists the worktree where the record's deletion started, residue also refuses while the PID it names runs, while a `git worktree remove` of the worktree runs, found by its arguments (`process::removing`), or while the activity probe sees a process using the worktree or its Git directory (`removed::unheld`). A live process with the PID it names is its run while that process's arguments hold `remove` (`process::removes`); where residue cannot read them, one that started more than ten minutes after the record was written is not, where residue can read start times (`process::started`). Where residue cannot tell, it refuses and names the move back by hand: another user wrote the record and residue is not root (`removed::foreign`), it reads the arguments of no other process, or the probe cannot show that no process uses the worktree (`Evidence::Unknown`). A trash restore also keeps such a purge off the worktree: it keeps the worktree's `.git` open from just after its hold (`restore::keep_open`), which every release's activity probe sees as a use; locks a worktree Git lists unlocked with `trash::LOCK` before it reads the records, lifting that lock on any later refusal (`restore::lift`); and once the worktree has moved, reads the records again and keeps and names a purge's record that came meanwhile (`removed::raced_purges`). On a filesystem with no flock(2) (`Taken::Unsupported`) no run removes or restores: a run plans a trash entry or record there as kept, with a warning and no change to its exit status (`Outcome::Kept`, `removed::unforgettable`), and a restore names the move back, or the recreate, by hand (`removed::Manual`). A remove run forgets an expired record only under its hold (`removed::forget_expired`). For a record with the hold line, a PID is never the guard: PIDs are reused, and a residue killed alone leaves its Git running.
- While a record lives, no removal, restore or forget by residue makes unreachable a commit the worktree's Git directory kept reachable. HEAD is pinned by `refs/residue/removed/ENTRY`; every commit its HEAD reflog names that no ref outside `refs/residue/` and no worktree's HEAD reaches, by `refs/residue/reflog/ENTRY/N` at each `merge-base --independent` tip (`removed::reflog_only`), whether or not another reflog names it: a branch's reflog goes with `git branch -D`. In a reftable repository, where Git reads no `logs/HEAD` file even when one is there (residue 0.0.7's restore wrote one after a `git refs migrate`), residue never reads it either: Git reads that reflog's new values and its oldest entry's old value (`git::head_reflog_commits`, in `removed::git_head_reflog`), never nothing, and every commit the worktree's reflogs name that the main worktree's do not counts too (`git::reflogs_commits`). The one case left: an old value after a gap in the middle (an expired entry, or one `git reflog delete` took) that another reflog also names is not pinned; that reflog keeps it reachable, so a later `git branch -D` or stash drop, or that reflog's expiry, can lose it. Git cannot read that old value on its own, and pinning every commit any reflog names would pin other branches' history in each record. Worktree-private refs (`refs/worktree/`, `refs/bisect/`, `refs/rewritten/`) and an operation in progress block removal (`inspect`). Removal never waits on this; it pins and goes on. Past `--keep-removed`, the later of the forgetting run's and the one the record was written with (its `keep` line; a record without one has only the run's, `removed::Item::expired`), forgetting drops the pins, and a commit only they held is left to `git gc`: the README says so. No run forgets a record before the `--keep-removed` it was written with. residue prints a command that clears Git's record of a worktree (`git worktree remove`; never `git worktree prune`) only where a removal record keeps what that drops. For a worktree whose directory is gone and that no record names, it names the repair or the mount first, then says when `git gc` or `git worktree prune` clears that record, by the rule Git applies (`output::prune_rule`), and names its HEAD reflog (`output::gc_note`), and no command that deletes.
- residue writes refs only under `refs/residue/removed/` and `refs/residue/reflog/`, only where none exists, and deletes only refs a record of its own names, only while each still names the commit the record names. Both go through `git::change_refs`: one `git update-ref --no-deref --stdin` transaction with old values, run with `core.fsync=reference` and `core.fsyncMethod=fsync`. Forgetting a record past `--keep-removed` is part of the confirmed plan, like the purge; `removed::drop_record` leaves a record and all its refs when any ref under its name is one it does not name or has moved, and `removed::discard` removes only the files residue wrote and the empty directory, never recursively. An entry with no `info` and no ref, an hour old, is the only one forgotten without a record.
- A removal record residue cannot read or forget never changes `remove`'s exit status: it is a warning on stderr and in JSON `warnings`, never in `errors`. `errors` and exit 3 stay about the PATHs and the trash.
- The stats ledger (`stats::path`, `ledger.jsonl`) never affects a removal or a restore. residue appends to it only after the deletion, move or restore succeeded (`stats::Run::record`, `restore::command`), never reads it to decide what to remove or restore, and a ledger it cannot read or write is a warning (stderr, `warnings`, `stats.error`, a restore note), never `errors` and never the exit status. Seeding only adds lines for removal records and trash entries the ledger lacks; it never changes them. A line is appended with one `write(2)` under `O_APPEND`, after a newline when the file does not end in one; a reader skips and counts a line it cannot parse and counts each `(event, repo, entry)` once. The ledger is opened only through `stats::open` (`O_NONBLOCK`, then a regular-file check), so nothing at its path can make a command wait.
- Nothing leaves the machine. The ledger and every record are local files, and residue's only network traffic is `watch`'s `git fetch` (`git::fetch`). A feature that would send anything anywhere needs an explicit decision recorded in the CHANGELOG.
- `residue restore` recreates a removed worktree only through `git::add_worktree` (`git worktree add`, never `--force`, never `-B`), and never moves, resets or deletes an existing branch: a branch at or ahead of the recorded HEAD is checked out, a rewritten one, or one another worktree has checked out, is left as it is and `BRANCH-restored` is created at the recorded HEAD, a deleted one is created again, and an occupied path refuses. One function, `removed::choose`, decides that, for the restore and for the `git worktree add` line it names where it can hold no record (`removed::recreate_line`). It writes the saved reflog back in front of the new one; a worktree it moves back gets the saved reflog and `config.worktree` back when its own are gone. The reflog goes by how the repository keeps its refs when restore runs (`git::is_reftable`), never by how it kept them when the record was written: `git refs migrate` can change it in between. In reftable, Git reads no `logs/HEAD` file, so restore writes none, says in its notes that the HEAD reflog was not put back, and keeps a record that holds a saved reflog (`removed::reftable_reflog`). It drops the record and refs only after the worktree's HEAD contains the recorded HEAD and Git reads the worktree's own HEAD reflog as naming every pinned commit (`removed::holds`, through `removed::git_head_reflog`, never the `logs/HEAD` file), whether recreated or moved back; otherwise the record stays. It reads the record's copies (`removed::read_copies`) before it changes anything, and refuses, changing nothing, when `info` or a copy the listing saw is gone: another run forgot or restored it first. Whether the record stays is said from its refs as Git has them then (`removed::refs_gone`): a record another run forgot meanwhile is never reported as kept, and the commits no ref keeps then are named. A path ENTRY is looked up from the nearest folder that exists; when that finds nothing, the current directory is searched, but neither is ever the home folder or a folder above it. A name, and the list, search the current directory, or, at or above the home folder, only `watch::default_roots` (`restore::Search`), never the home folder itself.
- The recovery line `scan` prints for an interrupted removal (`Leftover::recovery`, JSON `recovery`) is a command that works, and never a deletion: a `git worktree move` back, `git worktree remove` when its directory is gone and a removal record names it (which keeps its HEAD and reflog; with no such record it is empty, since that remove drops a HEAD and reflog nothing else keeps, and the text gives `Leftover::missing` and `Leftover::head` first), and when Git can no longer use it (`remove::unusable`: its `.git` file or HEAD is gone, so Git refuses the move) only the `residue restore` of its record, which says what to clear. While a run may still act on its record (`removed::Item::activity` is not `Idle`), and whenever residue cannot tell (an error), it is empty: any move then lets that run's Git delete the worktree where it lands. Text may tell a person to delete a directory; `recovery`, which a script may run, never does.
- A worktree `residue restore` put back carries `removed::MARKER` in its Git directory. It blocks only the work-landed rule (`remove::judge_upstream` under `--only-if-upstream-gone`, `watch`'s landed filter, its deadlines and the branches it fetches for); a marker residue cannot read counts as present. `watch`'s landed filter also keeps a worktree that a removal record lists as back at its path, or cannot tell is back (`removed::State::Back` and `Unknown`, from the scan's `removed[].state`), which covers a restore stopped between `git worktree add` and the marker; the child does not read records, so that guard is watch's alone. Disk pressure, `remove PATH` and a sweep still remove it.
- A removal record's state is `removed::Item::state`, one match over its files and Git's list of worktrees read when it is listed: `incomplete`, `unreadable`, `interrupted`, `back` (`removed::is_back`: a linked worktree with its checkout at its original path on the recorded branch, at or ahead of the recorded HEAD), `unknown` (one there whose HEAD Git could not compare; never read as `removed`) or `removed`. Only `removed` seeds a `freed` line (`stats::record_line`). `restore` of a `back` one without `--to` gives the worktree what it lacks (its marker, `config.worktree`, the saved reflog in front of its own), each step leaving alone what is there, and forgets the record only once `holds` passes; it refuses an `unknown` one without `--to`. No trash restore lands during a purge, since both hold the entry; a purge whose `git worktree remove` fails settles its record against the worktree in the trash, and its reason gives the entry's restore. `remove::standing` counts a listed path as the record's worktree only when its Git directory is the one the record was written for (`Written::is_its_git_dir`: canonical path, device and inode), so another worktree added at that path never stands in for it.
- `remove --all --yes` (an unattended sweep) refuses to run without `--idle`. `remove` without `--all` takes only worktree paths, never a scan root. `--idle` on `remove` implies `--trash` unless `--no-trash`.
- The `idle` check's last change is the newest of the checkout's entries, the files directly in the worktree's Git directory, and the timestamp inside the newest HEAD reflog entry (`inspect::last_change`). Never the mtime of anything under `logs/`: `git gc` rewrites every worktree's `logs/HEAD`. A last change residue cannot read is `unknown`.
- Regenerable rules come only from the built-in list, the user's config file, `--regenerable` and Git config files (`residue.regenerable`). Never from a file committed to the repository: a cloned repository must not be able to declare a user's files disposable. Never from the environment (`git -c`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_PARAMETERS`, the legacy `GIT_CONFIG`): every subprocess inherits it, so it must not widen what residue deletes. `git::environment_regenerable` reports those values on stderr and in `ignored_environment_rules`, so they are never ignored silently.
- The size walk (`fsinfo::measure`) never follows a symbolic link and never opens a folder by its full path, not even as a fallback. It opens the worktree one name at a time from `/`, and every folder in it with `openat` from its parent's descriptor with `O_NOFOLLOW`, checking its device and inode against the parent's listing. An open that fails, or finds another folder, makes `contents` `unknown`. A walk holds at most `HELD + REOPENED + 2` descriptors at any depth (`fsinfo::HELD`, `fsinfo::REOPENED`).
- Every string from the filesystem, Git or another process passes through `output::clean` before it reaches a terminal.
- Git runs through `git::command`: argv only, optional locks off, prompts off, hooks and fsmonitor disabled, inherited `GIT_DIR`-style variables, `GIT_CONFIG`, `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT` removed. `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM` stay, so residue reads the same config files as the user's Git.
- A worktree in the trash leaves it only through `trash::restore` (`git worktree move` back) or the purge (`trash::purge`: a re-check, then `git worktree remove` without `--force`). `trash::discard` removes only an entry's record and empty directories, never recursively. An entry that holds only its record files (`info`, `info.new`) is cleared only once it is `removed::INCOMPLETE_AFTER` old (`trash::Item::clearable`: its `trashed` time, or its directory's when `info` is missing or damaged), so a purge never takes an entry another run is moving a worktree into; `info` is written as `info.new`, synced and renamed, like a removal record's. The purge is part of the confirmed plan, so a preview or an unconfirmed run purges nothing. A run that confirms another run's plan takes that plan's `generated_at` as `--as-of` (`Mode::as_of`, never later than its own start): it measures every age then, `--idle` included, and purges or forgets only an entry or record whose directory, and for a record the repository's `worktrees/`, last changed before it (`remove::before`), so it takes nothing that plan could not list. A worktree in the trash or under a hidden `.residue-removing-` name is never a target of `remove`, by PATH or by sweep (`discover::Repo::new` sorts them out).
- Every lifecycle's state is read from Git and the filesystem right before a move, never from a stored field or an earlier listing. Each move is one Git command or one `rename(2)`, `mkdir(2)` or `O_EXCL` create, so a second writer's move fails and is reported. [CONTRIBUTING.md](CONTRIBUTING.md#state-machines) names each lifecycle, where its states are read and which functions move it; a change that adds a state or a move updates that table.
- One dependency (`libc`). Add another only when hand-written code would be riskier.
- The Mac app, in [residue-ui](https://github.com/whiteheap/residue-ui), bundles one residue-cli release that it pins, and never reimplements a check, a size or a deletion: it reads `--json`, exit statuses and a few result lines. Keep them a contract, as [CONTRIBUTING.md](CONTRIBUTING.md#open-a-pull-request) says: add, never rename or remove. A change reaches the app only once residue-ui pins the release that has it.

## Layout

| File | Owns |
| --- | --- |
| `src/cli.rs` | Argument parsing and help text |
| `src/commands.rs` | `scan`, `explain`, and resolving a PATH to one linked worktree |
| `src/remove.rs` | The remove plan, confirmation, re-check, move aside, removal record, execution, the trash purge, forgetting expired removal records, and interrupted-removal recovery (`Leftover`) |
| `src/trash.rs` | The trash: entries and their records, moving one back, and the purge |
| `src/removed.rs` | Removal records and their refs (`refs/residue/removed/`, `refs/residue/reflog/`): writing, listing, forgetting, recreating a worktree from one with its reflog, and the restored marker |
| `src/hold.rs` | A run's hold on a trash entry or removal record (flock(2) on its `info`), and passing it to the `git worktree remove` that deletes the worktree |
| `src/restore.rs` | `residue restore`: listing trash entries and removal records together, choosing one, and its text and JSON |
| `src/stats.rs` | The stats ledger of what residue freed (where it is, its lines, appending, seeding from removal records and trash entries, totals), `residue stats`, the line a `remove` run ends with, and the lines `scan` and `service status` show |
| `src/inspect.rs` | Every check and the verdict |
| `src/activity.rs` | The process probe (`lsof` on macOS, `/proc` on Linux, `ps` plus the `kern.proc.filedesc` and `kern.proc.vmmap` sysctls per process on FreeBSD, `ps` plus a working-directory sysctl per process on NetBSD, OpenBSD and DragonFly, `/proc/PID/path` on illumos) |
| `src/process.rs` | Other processes' arguments and start times (`/proc` on Linux and illumos, sysctl on macOS and the BSDs): a `git worktree remove` of a worktree whose record has no hold, and whether a PID started after a record |
| `src/git.rs` | Hardened Git invocation, the non-interactive fetch `watch` runs, and porcelain parsers |
| `src/fsinfo.rs` | Disk usage walk and free space |
| `src/policy.rs` | Regenerable rules (names and paths) for ignored entries |
| `src/discover.rs` | Finding repositories under a root |
| `src/output.rs`, `src/json.rs` | Terminal text and JSON documents |
| `src/run.rs` | Child processes with a deadline and an output cap, and `run::spawn`, the one place a child starts, under a lock that keeps a child from inheriting another's pipes on macOS. `clippy.toml` refuses `Command::spawn`, `output` and `status` anywhere else (#114) |
| `src/watch.rs` | `residue watch`: when to remove (branch landed, disk low), by running `scan --json` and `remove --yes --idle --no-trash`; when to fetch (`Fetcher`); the default roots |
| `src/events.rs` | Waiting for file changes: inotify on Linux, kqueue on macOS and the BSDs. kqueue holds an open file per watched path, so `Events::room` raises the soft open-file limit and keeps 128 of it free for the children a pass starts |
| `src/jsonread.rs` | Reading back residue's own JSON documents, for `watch` |
| `src/service.rs` | `residue service`: the launchd agent and the systemd user service that run `watch`, reading an installed one back (`status`, kept roots), the fingerprint `install --expect` compares and the lock install and uninstall take, and the line `scan` ends with at a terminal while no `watch` runs (`hint`) |
| `scripts/race-check.sh` | The race check: changes a worktree while the release binary's prompt waits, under a pseudo-terminal |
| `scripts/partial-probe.sh` | Sourced by the five test scripts: `$partial_probe` on NetBSD, OpenBSD and DragonFly, where nothing is a candidate, and the named reason each removal-expecting case is skipped with |
| `packaging/` | Linux packages (`nfpm.yaml`, `linux-packages.sh`), the signed apt, dnf and pacman repositories (`apt-repo.sh`, `rpm-repo.sh` with `rpm/residue.repo`, `arch-repo.sh`), their public key (`signing-key.asc`), the scripts that publish them to whiteheap/whiteheap.github.io (`publish-repositories.sh`, `wait-for-repositories.sh`) with GitHub's pinned SSH host keys (`github-known-hosts`), and the AUR package (`aur/`) |

## Text and cost

- Text for a person is brief: a heading of a few words, a sentence or two under it, one line per result, each caveat beside its action, and detail one step away (the README, `--help`, `--json`, `residue explain`). Brief never drops a warning or a limit, and keeps residue's terms: candidate, keep, unknown. A wording change leaves `--json`, exit statuses and the lines the app reads alone (#77).
- CPU and memory belong to the user, and residue runs in the background. Measure a change to a hot path, or one that adds a dependency, a thread, a child process or a timer, before and after: both builds interleaved on one machine, three runs or more each, every run in the pull request, system CPU apart from user CPU, and how you checked the output is the same. On macOS `/usr/bin/time -l` gives wall time, CPU and residue's own `peak memory footprint`; `GIT_TRACE2_EVENT=FILE` logs each git process. A change that makes a number worse says why it is worth it (#75). [CONTRIBUTING.md](CONTRIBUTING.md#performance) has the fixture, the commands and main's numbers to compare with.
- File an issue for a slow or heavy component you find, in residue, a library or a tool it runs, with the measurement and the command that repeats it, before there is a fix.

## Verify a change

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo build --release
sh .github/smoke.sh ./target/release/residue
sh .github/watch-smoke.sh ./target/release/residue
bash scripts/race-check.sh ./target/release/residue
bash scripts/contract-check.sh ./target/release/residue
bash scripts/recovery-check.sh ./target/release/residue
```

On macOS, run the scripts with `/bin/bash`, as CI's `bash` there is: it is bash 3.2, which rejects some forms a newer bash on your PATH accepts, such as a `case` inside `$(...)`.

CI runs the format, lint, test and build steps, both smoke tests, the race, contract and recovery checks on macOS and on Ubuntu 24.04 and 26.04, x86_64 and arm64, and the build, both smoke tests and the race, contract and recovery checks in FreeBSD 14, NetBSD 10, OpenBSD 7.8 and DragonFly 6.4 virtual machines as root and as an ordinary user. An OmniOS (illumos) virtual machine runs the build, `.github/smoke.sh` and the contract and recovery checks, as root and as an ordinary user: illumos has no change events for the watch smoke test's two-minute limit, and its `script` cannot drive the race check. On NetBSD, OpenBSD and DragonFly each script skips the cases that expect a removal or a prompt, by name (`scripts/partial-probe.sh`), and checks that a clean idle worktree is kept as `unknown` (`partial_probe`). NetBSD and OpenBSD run the race check through `.github/script-adapter/script`, which translates the `script -q FILE CMD...` call into their `script -c` form. It runs `.github/service-smoke.sh` (install, status, uninstall) on macOS and Linux x86_64. Never run that script, or `residue service install` or `uninstall`, `--dry-run` included, on a machine whose service you use: they replace or remove this user's service.

A change to `src/remove.rs`, `src/trash.rs`, `src/removed.rs`, `src/restore.rs` or `src/hold.rs`, or to how `src/git.rs`, `src/run.rs` or `src/watch.rs` move, lock, unlock or remove a worktree or stop a remove run, also runs `bash .agents/skills/verify-removal-races/check.sh`, about a minute. It model-checks every order of the steps of a removal, a purge, both restores and Git's own delete, and fails when a rule breaks that did not before. It reads the model, not the Rust: update the model in the same change, as [its skill](.agents/skills/verify-removal-races/SKILL.md) says, and that skill lists the races it has found. `.github/workflows/model.yml` runs it when the model changes; it is not a required check.

Then run the binary on real repositories. Make a scratch repository with worktrees in the states your change touches; [CONTRIBUTING.md](CONTRIBUTING.md#verify-a-change) has a script that builds one with each common state. [docs/platforms-and-testing.md](docs/platforms-and-testing.md) records the states each version covered. Run `scan`, `explain` and `remove`, and record the exact platform and Git version that ran. For Linux from a Mac: `cargo zigbuild --release --target aarch64-unknown-linux-musl`, then run the binary in an `ubuntu:24.04` container as a non-root user.

## A security issue

A bug that [SECURITY.md](SECURITY.md) calls a security issue goes into a draft security advisory (**Security**, **Advisories**, **New draft security advisory**), never a public issue. Its pull request and commits say what changes, not how to make residue lose data. Publish the advisory with the release that fixes it, naming that release. #135 to #139 went out as public issues on 2026-11-08, before this rule.

## Release

1. On a branch, bump `version` in `Cargo.toml`, run `cargo build` to update `Cargo.lock`, turn `## Unreleased` in `CHANGELOG.md` into a `## X.Y.Z (date)` section (add the section if there is no `## Unreleased`), and update the `--tag` in the `cargo install` lines of the README and `docs/installation.md`. The release notes come from that section, so it opens with what a user gets: one line, then a short list of the main changes and anything that works differently from the last release, each with its issue number. The detailed entries follow under `### Details`. Open a pull request. `main` is protected: a change lands only through a pull request, with the `macos-latest`, `ubuntu-24.04` and `ubuntu-24.04-arm` checks green, and never by a direct or force push. Wait for `freebsd-14` too, though the ruleset does not require it. Squash merge it.
2. Tag the merge commit on `main`, not the branch: `git fetch origin`, check that `origin/main` is the squash commit, then `git tag -s vX.Y.Z -m "residue X.Y.Z" origin/main` and `git push origin vX.Y.Z`. `.github/workflows/release.yml` builds four targets, attests provenance for all four, and publishes the GitHub release with `SHA256SUMS`. It publishes no Mac app: 0.0.10 is the last release with `residue-macos.dmg`. A pull request that changes it, and `gh workflow run release.yml --ref BRANCH`, are dry runs that attest and publish nothing. Its last job starts `.github/workflows/packages.yml` as a separate run on `main` (check that run too), which builds `.deb`, `.rpm` and Arch packages from the two Linux archives and the FreeBSD x86_64 and aarch64 archives, each built and smoke-tested in a FreeBSD 14 virtual machine of its architecture from the tag's source (aarch64 emulated, so it is the slowest leg), attests them, and adds them to the release with an updated `SHA256SUMS`. A failed FreeBSD build never holds back the Linux packages or the other FreeBSD archive; check that both archives are there. `gh workflow run packages.yml --ref BRANCH -f tag=vX.Y.Z -f dry_run=true` checks a change to that workflow without uploading or deploying anything. When the tag is the latest release, its `repositories` job then rebuilds the signed apt, dnf and pacman repositories from those packages and pushes them to `residue/` in whiteheap/whiteheap.github.io, whose GitHub Pages site serves them at https://whiteheap.github.io/residue/ (`apt/`, `rpm/`, `arch/`), then waits until it does. That address does not depend on this repository's name. They hold only the latest release, so users get it with `apt upgrade`, `dnf upgrade` or `pacman -Syu` and no release needs a manual step. To package a release made before that workflow existed, run `gh workflow run packages.yml -f tag=vX.Y.Z`. To publish the repositories again from the packages already in the latest release, building and uploading nothing, run `gh workflow run packages.yml -f tag=vX.Y.Z -f republish=true`.
3. crates.io: the `crates` job in `.github/workflows/release.yml` publishes the tag's crate after the GitHub release, through Trusted Publishing: it runs in the `crates-io` environment, which only `v*` tags can use, and crates.io gives it a token for that run alone. Check the job, then that https://crates.io/crates/residue shows the new version. It runs only while the repository variable `CRATES_TRUSTED_PUBLISHING` is `true`, and it stays off until the crate exists: crates.io sets up Trusted Publishing only for a crate that exists, so the first publish goes out by hand. A version on crates.io can be yanked but never replaced, so a failed or wrong publish is fixed by the next release.
4. The tap updates itself: `.github/workflows/update-residue.yml` in [whiteheap/homebrew-tap](https://github.com/whiteheap/homebrew-tap) runs every hour at :23, writes the new tag and the four checksums from `SHA256SUMS` into `Formula/residue.rb`, runs `brew style`, `brew audit --strict --online`, `brew install` and `brew test`, and pushes the commit. To have it now, run `gh workflow run update-residue.yml -R whiteheap/homebrew-tap` and watch that run. Then check that the formula names the new tag in its four URLs. It has no `version` line: Homebrew reads it from the URL, and `brew audit --strict` rejects a redundant one. After the tap update, upgrade this machine's install, so the copy we dogfood is always the latest release:

   ```sh
   brew update && HOMEBREW_NO_AUTO_UPDATE=1 HOMEBREW_NO_INSTALL_CLEANUP=1 brew upgrade whiteheap/tap/residue
   ```

   When residue is not installed, use `brew install` in place of `brew upgrade`, with the same two variables. Use exactly this form: the machine's brew hook allows a tap upgrade only this way. Auto-update and install-time cleanup could change other formulae in the shared `/opt/homebrew`. The formula is one static binary with no `depends_on`, so the upgrade itself changes nothing else in the prefix.

   A `residue watch` that 0.0.11 or later started exits between passes once the upgrade replaces its binary, and launchd or systemd starts the new release ([After an upgrade](docs/automation.md#after-an-upgrade)). Only a watch that 0.0.10 or earlier started keeps the code it started with: restart it while no pass is running, that is while `pgrep -P PID` prints nothing for the PID that `residue service status` shows, with `launchctl kickstart -k gui/$(id -u)/com.whiteheap.residue.watch`. Either way, `residue service status` then shows a new PID, and `lsof -p NEWPID | grep Cellar/residue` names the new version. On 2026-11-08 the 0.0.7 service kept running after the 0.0.8 upgrade until this restart.
5. Optional, once [#1](https://github.com/whiteheap/residue-cli/issues/1) is done: update the AUR package `residue-bin`. Arch and Omarchy users already get each release from the pacman repository; the AUR adds `yay -S residue-bin` for people who have not added it. It is not on the AUR yet, because AUR registration is closed: the first push creates it. Run `packaging/aur/update.sh vX.Y.Z` (needs `gh` and Docker), commit `packaging/aur/`, then push the same `PKGBUILD` and `.SRCINFO` to the AUR. That needs an AUR account with your SSH key:

   ```sh
   git clone ssh://aur@aur.archlinux.org/residue-bin.git /tmp/residue-bin
   cp packaging/aur/PKGBUILD packaging/aur/.SRCINFO /tmp/residue-bin/
   git -C /tmp/residue-bin add PKGBUILD .SRCINFO
   git -C /tmp/residue-bin commit -m "Update to vX.Y.Z" && git -C /tmp/residue-bin push
   ```
6. The Mac app bundles a residue-cli release, so it gets this one only through [residue-ui](https://github.com/whiteheap/residue-ui): there, a change bumps `sidecar.lock` to the new tag, and residue-ui releases on its own.

### The package signing key

The apt, dnf and pacman repositories, and the `.rpm` files in the dnf repository, are signed with one ed25519 key, fingerprint `1AEAB31435118A1FE575D36EE1553632FC32554A`, with no expiry date: an expired key would break every user's upgrades at once. The public key is `packaging/signing-key.asc`, published as https://whiteheap.github.io/residue/residue-signing-key.asc and, for apt, as `apt/residue-archive-keyring.gpg`. The `repositories` job checks every signature against it before publishing. The armored private key is the `PACKAGE_SIGNING_KEY` secret of the `github-pages` environment, next to `PAGES_DEPLOY_KEY`, the write deploy key for whiteheap/whiteheap.github.io, so only that job can read them, and the `github-pages` environment admits only `main` and `v*` tags. A backup is in the maintainer's macOS keychain, item `Whiteheap residue apt signing key` (base64 of the armored key).

To rotate it, generate a new key, replace `packaging/signing-key.asc`, update the secret with `gh secret set PACKAGE_SIGNING_KEY --env github-pages --repo whiteheap/residue-cli`, update the fingerprint in the README, and tell users to fetch the key again. Their upgrades fail until they do.

To replace the deploy key, generate an ed25519 key, add its public half as a write deploy key on whiteheap/whiteheap.github.io in its web settings (a key added with `gh` is removed when that `gh` authorization is revoked), and run `gh secret set PAGES_DEPLOY_KEY --env github-pages --repo whiteheap/residue-cli`. The organization must allow deploy keys, under Settings, Member privileges.
