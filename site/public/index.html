residue removes a worktree only when nothing in it would be lost, whichever coding agent left it.

automatic

Install it as a service, and residue cleans up on its own, in two cases only:

  • The work landed. The upstream branch is gone from the local refs, and the worktree has not changed for an hour.
  • The disk is low. Free space is below 10%. Worktrees unchanged for two days go, largest first, until there is room again.

Each removal runs residue remove with every one of its checks. These removals delete: they do not use the trash. Branches, commits and locked worktrees stay. Each removal leaves a record, so for 30 days residue restore brings the worktree back.

See what it would remove first; when it would remove nothing, it says why:

residue watch --once --dry-run

Then turn it on:

residue service install

That starts residue watch now and at every login, with launchd on macOS and systemd on Linux. It watches the usual code folders in your home folder that exist, such as ~/src, ~/code and ~/Work, and prints which, along with what it removes and how to preview it. If your code lives elsewhere, name its folder, which replaces the list: residue service install ~/src. watch runs only when you start it or install it as a service; scan never starts it.

The install script turns it on for you. To install without it:

curl -fsSL https://residue.whiteheap.com/install.sh | sh -s -- --no-service

To turn it off later: residue service uninstall.

Reclaim storage automatically

what it keeps

residue deletes only what its checks show you can get back.

  • Committed files and rebuildable output. A worktree goes only when every tracked file is committed and every ignored entry matches a regenerable rule, such as node_modules/. An ignored .env keeps it, even inside build/. A check residue cannot finish keeps it.
  • Branches, commits and the stash stay. residue never deletes a branch, never kills a process, and never lifts a lock it did not set. Lock a worktree to keep it.
  • What you saw, or nothing. Right before each removal, residue runs every check again. Any change keeps the worktree, and the reason names it.
  • A record to restore from. Every removal leaves one, watch's included: for 30 days, residue restore recreates the worktree at its path, on its branch and HEAD. Ignored files such as node_modules/ are not kept; the project's install makes them again.
  • A trash for the whole worktree. With --trash, which --idle turns on, the worktree itself waits in the trash, every file included, until a later run purges it, after seven days by default.

look first

residue needs Git 2.36 or later on PATH; on Ubuntu 22.04, add ppa:git-core/ppa first. Windows is not supported; the install script points to WSL. Debian, Ubuntu, Fedora, Arch, prebuilt binaries and building from source are in the other ways to install, and downloads are on the latest release.

residue scan ~/src/app

Replace the example path ~/src/app with your repository's path. scan deletes nothing: it lists each linked worktree with its size, its verdict and the reason, and every directory is still there afterwards.

residue explain PATH

Replace PATH with a linked worktree's path to see every check, and why it passed or failed.

mac app

residue in a window.

The Mac app lists the linked worktrees under your code folders with their size and verdict, moves the ones that can go to the trash, restores them, and turns automatic cleanup on or off. Every check and removal comes from the residue inside it, nothing moves until you confirm, and automatic cleanup deletes without the trash. macOS 13 or later, on Apple silicon and Intel.

how it works

  1. Find and measure.

    residue inspects the linked worktrees Git lists for each repository, and their disk use.

  2. Understand the decision.

    A worktree is a candidate only when every check passes. A failed check keeps it, and so does a check residue could not complete, shown as unknown. Each verdict comes with its reason. What makes a worktree a candidate

  3. Choose what happens next.

    residue remove shows the plan and asks first, checks the worktree again, and hands the deletion to git worktree remove without --force. With --trash, the worktree stays restorable until the purge. What removal deletes, and what it keeps

where it fits

residue is a standalone command, or a login service that runs that command. It does not create worktrees and it does not merge branches.

  • Claude Code, when you only want the worktrees that tool created, swept and locked by that tool.
  • Codex app, when you want the worktrees Codex manages kept to the newest 15, with a snapshot saved before each one is deleted.
  • Cursor, when you want the worktrees on the machine kept to the newest 25, the oldest removed first.
  • Worktrunk, when you want to create, switch, merge, and remove worktrees, and stop processes tied to one.
  • residue, when you want linked worktrees from any tool removed only when every check passes, with Git doing the delete and a trash on a sweep.

Codex and Cursor decide by age and count. residue decides by what is in a worktree, whichever tool made it, and never deletes a branch.

Where it fits

before you remove anything

residue deletes directories. Start with scan and explain, and read the removal limits before you remove a worktree or turn on the service. The activity check cannot see every process or a paused session, and a write can still land after the last check. Reclaimable space is an estimate. residue runs as you; it is not a security boundary between users.
